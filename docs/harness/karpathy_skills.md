# 안드레 카파시(Andrej Karpathy) 행동지침

## 4대 원칙

### 1️⃣ Think Before Coding

첫 번째는 코딩하기 전에 생각하라는 규칙이다.

요구사항이 애매한데도, Claude가 스스로 해석해서 바로 구현을 시작하는 경우가 있다.

이를 막기 위한 장치라고 생각하면 된다.

- 가정을 명시하기
- 불확실하면 질문하기
- 여러 해석이 가능하면 선택지를 제시하기

해당 부분은 Karpathy가 말한 “AI는 혼란을 관리하지 못하고, 질문하지 않는다”는 문제를 담고있는 것 같다.

### 2️⃣ Simplicity First

두 번째는 단순함을 우선하라는 규칙이다.

간단한 기능 하나를 요청했는데, 불필요한 확장·추상 클래스를 함께 만들어버리는 경우가 있다.

해당 규칙은 과잉 구현을 명확히 금지한다.

- 요청받지 않은 기능 추가 금지
- 한 번만 쓰는 코드에 추상화 금지
- 요구하지 않은 유연성·설정화 금지
- 불가능한 시나리오에 대한 과한 예외 처리 금지
- 200줄로 작성했는데 50줄로 가능하다면 다시 단순화

개인적으로 가장 마음에 들었던 문장은 아래 기준이다.

> Would a senior engineer say this is overcomplicated?

즉, AI에게 “시니어 개발자가 봤을 때 과한 설계인가?”를 스스로 점검하게 만드는 것이다.

### 3️⃣ Surgical Changes

세 번째는 수술하듯 필요한 부분만 수정하라는 규칙이다.

AI Agent에게 기존 코드를 맡겼을 때 가장 무서운 부분은 작업 범위가 너무 광범위해진다는 것이였다.

해당 규칙은 이를 명확하게 금지하고 있다.

- 꼭 필요한 파일과 라인만 수정하기
- 주변 코드, 주석, 포맷팅을 임의로 개선하지 않기
- 깨지지 않은 코드를 리팩토링하지 않기
- 기존 스타일이 마음에 들지 않아도 맞춰가기
- 관련 없는 dead code는 삭제하지 말고 언급만 하기

여기서 핵심 기준은 매우 명확하다.

> Every changed line should trace directly to the users request.

즉, 변경된 모든 라인은 사용자의 요청과 직접 연결되어야 한다는 의미다.

### 4️⃣ Goal-Driven Execution

네 번째는 목표 기반으로 실행하라는 규칙이다.

이 부분이 Karpathy의 생각과 가장 직접적으로 연결된다고 느꼈다.

Karpathy는 AI에게 세부 구현을 지시하기보다, 성공 기준을 주고 반복하게 하라고 말했다.

forrestchang의 Skill도 동일하게 작업을 검증 가능한 목표로 바꾸도록 유도한다.

- validation 추가 → "잘못된 입력에 대한 테스트를 작성하고 통과시키기"
- 버그 수정 → "버그를 재현하는 테스트를 작성하고 통과시키기"
- 리팩토링 → "수정 전후 테스트가 모두 통과하는지 확인하기"

멀티 스텝 작업에서는 아래처럼 각 단계마다 검증 기준을 두는 방식이다.

1. 요구사항 분석 → verify: 불확실한 부분 질문
2. 최소 변경 구현 → verify: 변경 범위 확인
3. 테스트 실행 → verify: 기존 테스트 통과

## 바이브 코딩 실천 규칙

4대 원칙을 이 프로젝트의 "바이브 코딩" 협업 방식에 맞게 구체화한 실천 규칙이다.

- **의도는 자연어로, 검증은 코드로**: 요구사항은 자연어로 편하게 전달해도 되지만, 결과물은 반드시 실행하거나 테스트로 검증한다.
- **AI를 주니어 개발자로 취급한다**: AI가 만든 결과를 무조건 신뢰하지 않고 사람이 최종 확인·승인하며, 의심스러운 결과는 재작업을 요청한다.
- **작은 단위로 반복한다**: 한 번에 큰 기능을 통째로 요청하지 않고 작은 단위로 나누어 요청하고 매 단계마다 결과를 확인한다.
- **막히면 즉시 질문한다**: 요구사항이 모호하면 AI가 임의로 해석해서 진행하지 않고 먼저 질문하거나 선택지를 제시한다. (1️⃣ Think Before Coding과 연결)
- **속도 판단("내가 직접 하면 더 빠를 것 같다")을 근거로 오케스트레이션(병렬 서브세션·전문 에이전트)을 생략하지 않는다(2026-08-28 강화 — 적용 범위를 "판단이 필요 없는 작업"에서 판단이 필요한 작업까지로 넓혔다).** 커밋→동기화→감사 같은 판단 없는 기계적 체인뿐 아니라, "이건 내가 이미 맥락을 다 파악하고 있어서 직접 하는 게 낫겠다"고 스스로 판단해 포그라운드에서 처리하기로 한 작업(코드 리팩터링 등 판단이 필요한 작업 포함)도 기본적으로 병렬 서브세션이나 전문 에이전트로 위임한다. 여기서 "병렬 서브세션"은 Claude Code의 대화 분기 기능을 가리키며, `git-workflow.md` 10절이 이미 정의해둔 것과 같은 개념이다 — 그 절이 "하네스를 다른 프로젝트로 포크한다"(코드/파일 복사)와 혼동을 피하려고 "fork" 대신 이 용어를 쓰기로 한 이유가 여기서도 그대로 적용된다. Agent 도구 자체가 "즉시 반환 + 완료 시 알림"으로 설계돼 있어(호출 즉시 결과를 기다리지 않고 다음 턴으로 넘어가며, 작업이 끝나면 별도 알림으로 통보받는다), 사용자 질문이 중간에 끼어들어 대화가 다른 주제로 길게 이어지더라도 던져둔 체인은 그대로 진행돼 잊힐 위험이 없다 — "나중에 해야지"라고 마음속으로만 기억해두는 것에 기대지 않는 구조적 안전장치다. **이 안전장치는 판단이 필요한 작업일수록 오히려 더 절실하다** — 완료까지 시간이 걸리는 만큼 그 사이 다른 대화 주제가 끼어들 여지가 크고, 포그라운드에서 직접 처리하면 이 알림 안전장치 자체가 아예 작동하지 않아 완료 후 이어서 하기로 한 후속 조치(자동 트리거 재감사 등)를 놓치기 쉽다.

  **근거(2026-08-28)**: 이 프로젝트에서 report-tools 스크립트 5개 리팩터링을 "이미 맥락을 다 파악했으니 직접 하는 게 빠르다"고 판단해 포그라운드에서 처리했다. 작업 자체는 문제없이 끝났지만, 그 직후 이어서 돌리기로 한 자동 트리거(재감사)를 사용자의 다른 질문(Vercel 배포 구조, 카카오톡 멘트 라벨)에 밀려 놓쳤다 — 사용자가 "진행하고 있어??"라고 직접 확인할 때까지 아무 에이전트도 돌고 있지 않았다. 판단이 필요하다는 이유로 오케스트레이션을 생략한 것 자체가 이 사고의 원인이었다고 사용자가 지적하며, 직접 처리하는 게 더 빠르다는 자체 판단을 근거로 위임을 생략하지 말고 판단 필요 여부와 무관하게 항상 오케스트레이션하라고 명시적으로 요청해 원칙을 강화했다.

  **`git push`는 이 체인에 절대 포함하지 않는다** — `CLAUDE.md` 금지 항목·`git-workflow.md` 3-1절의 "push는 매번 명시적 허락을 받는다" 원칙은 병렬 서브세션 안에서도 예외 없이 적용된다. 체인이 커밋·동기화·감사까지는 자동으로 진행되더라도, push 직전에는 반드시 멈추고 사용자 승인을 기다린다 — "자동 실행"과 "push 승인 생략"은 서로 다른 문제이며 이 원칙이 후자를 덮어쓰지 않는다.

  **"지금 바로 ~할게요"라고 답한 순간과 실제로 그 행동을 하는 순간 사이에 시차를 두지 않는다(2026-08-28 범위 확대 — 에이전트 디스패치에 한정하지 않고, 완료된 서브에이전트 결과물 게시·커밋·파일 반영 등 메인 세션이 직접 실행하는 즉시 조치 전부에 적용).** 여러 요청이 한꺼번에 밀려드는 상황(사용자가 짧은 간격으로 메시지를 연달아 보내는 경우 등)에서, 어떤 조치를 약속한 직후 다른 요청 처리에 먼저 손을 대다가 그 약속 자체를 잊고 넘어가는 실수가 날 수 있다. "지금 바로 디스패치할게요"·"지금 바로 게시할게요" 같은 문장을 쓴 응답 안에서는 그 문장이 나온 같은 턴 안에 실제 행동(Agent 호출, `Artifact` 게시, 커밋 등)까지 마친다 — 말로 약속만 하고 다음 턴으로 미루지 않는다.

  **근거(2026-08-28 추가)**: `ui-ux-designer`가 아티팩트 v3 탭을 로컬 파일로 완성했다는 완료 알림을 받고 "지금 바로 게시할게요"라고 답했으나, 같은 턴에 실제 `Artifact` 게시 호출을 하지 않고 파일 존재만 확인한 채 바로 이어진 사용자의 다른 질문(Vercel 환경변수 등) 처리로 넘어가 버렸다 — 이후 여러 턴 동안 실제 게시가 누락된 채 방치됐고, 사용자가 직접 그 링크를 열어보고 "아직 그대로인데?"라고 지적한 뒤에야 발견·처리됐다. 위 원칙이 "에이전트 디스패치"라는 좁은 표현에 머물러 있어 "게시"처럼 메인 세션이 직접 하는 다른 즉시 조치에는 적용되는지 모호했던 것이 원인으로 판단해, 적용 범위를 명시적으로 넓혔다.
- **반복되는 문제는 발견 즉시 하네스에 반영한다**: 같은 종류의 버그·누락이 서로 다른 시점에 다시 나타나면(예: 기기·브라우저별로 계속 재현되는 뷰포트 버그, 배포 URL을 매번 다시 찾아야 하는 것), 그 자리에서 문제만 고치고 넘어가지 않고 재발을 막을 규칙·습관을 관련 하네스 문서(`docs/harness/`)에 바로 적어둔다 — "다음엔 조심해야지"라고 마음속으로만 기억해두지 않는다. `git-workflow.md` 9절("같은 유형의 실수가 2~3회 이상 반복되면 전담 에이전트를 만들 신호")은 이 원칙을 **에이전트 신설**이라는 특정 해법에 적용한 사례이고, 이 규칙은 그보다 넓게 적용된다 — 해법이 새 에이전트가 아니라 기존 문서의 새 절, 체크리스트 항목, 코딩 관례일 수도 있다. 무엇을 반영할지 애매하면(사소한 일회성 실수인지, 재발 방지가 필요한 패턴인지) 사용자에게 먼저 확인한다. **버그의 진단 시행착오 자체(무엇을 의심했다가 왜 틀렸는지, 최종 원인이 뭐였는지)를 증상 기준으로 남기고 싶으면 `docs/harness/bug-log.md`를 쓴다** — 이 파일은 "앞으로 이렇게 코딩해라"는 처방이 아니라 "이 증상을 만나면 과거에 뭘 시도했다가 틀렸는지" 검색용 로그라 목적이 다르다.
