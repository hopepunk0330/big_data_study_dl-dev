# 노션 프로젝트 관리 방식 (재사용 가능한 패턴)

프로젝트마다 관리용 Notion 페이지를 하나씩 두고, 거기에 사용자와 Claude가 함께 기획·문서화 작업을 하는 방식의 운영 규칙. Notion MCP로 작업할 때 이 문서를 먼저 참고한다.

**이 페이지는 단순 작업 메모가 아니라, 실제 평가받는 진행 보고서나 팀원 공유 문서가 될 수 있다는 전제로 관리한다** — 지금은 사용자 혼자 보는 것 같아도, 정리 마감일·평가 시점에 링크로 제출되거나 팀원에게 공유될 수 있다. 그래서 아래 서식·명목화 규칙(4-2절 등)은 "지적받았을 때만" 지키는 게 아니라, 그 규칙을 새로 확정하거나 강화한 순간 이미 작성된 페이지 전체에 스스로 적용한다 — 지적받은 예시 하나만 고치고 나머지는 그대로 두지 않는다.

**단, 이 원칙은 1절의 절대 규칙보다 우선하지 않는다.** "페이지 전체에 스스로 적용한다"는 건 **Claude가 작성했거나 Claude 몫으로 명시된 콘텐츠**(회색 비강조 설명, Claude가 만든 하위 페이지·섹션 등 — 1절이 정의한 예외 범위)에 한정된다. 사용자가 직접 쓴 원문은 서식 규칙이 새로 강화됐다는 이유만으로 손대지 않는다 — 사용자 원문에도 같은 규칙을 적용하고 싶다면 1절대로 먼저 사용자에게 제안하고 승인받는다.

## 1. 절대 규칙 — 기존 내용은 건드리지 않는다

**이미 작성되어 있는 글·블록·페이지는 절대 수정하거나 삭제하지 않는다.** 사용자가 명시적으로 "이 부분 고쳐줘"라고 지목하지 않는 한, Notion 작업은 항상 **추가(append)만** 한다.

- 페이지 안에 기존 텍스트가 있으면 그 내용을 요약·재작성하거나 형식을 "정리"한다는 명목으로 바꾸지 않는다.
- 기존 블록의 순서를 임의로 옮기거나, 기존 제목을 통일감 있게 바꾸는 것도 금지 — 사용자가 쌓아온 원문 그대로 둔다.
- 새로 쓸 내용은 새로운 섹션/블록/하위 페이지로 덧붙인다.
- 애매하면(예: "이 초안, 다듬어서 다시 써줘" 같은 요청이 없는 상태에서 기존 문장이 어색해 보일 때) 고치지 않고 그대로 두거나, 먼저 사용자에게 확인한다.

**예외 — Claude가 직접 만든 페이지/섹션은 계속 갱신할 수 있다.** 이 절대 규칙은 "사용자가 직접 쓴 기존 글"을 보호하기 위한 것이지, Claude 스스로 만들어서 지속적으로 최신화하기로 한 산출물(예: 테스트 보고서 동기화 페이지처럼 반복적으로 내용을 갱신하는 용도로 만든 페이지)까지 막는 게 아니다. 다만 어떤 페이지/섹션이 "Claude가 만들어서 계속 갱신해도 되는 것"인지 헷갈리지 않도록:
- Claude가 만드는 페이지/섹션은 사용자 원문과 섞어 넣지 않고 **별도 페이지 또는 명확히 구분되는 섹션**으로 만든다.
- 처음 만들 때 "이 페이지/섹션은 Claude가 계속 갱신함"이라고 알 수 있게 표시해둔다(제목이나 첫 줄에 명시).
- 애매하면(이게 Claude가 계속 갱신해도 되는 페이지인지 확신이 안 서면) 갱신하지 않고 먼저 사용자에게 확인한다.

## 2. 새 페이지는 어디에 만들지

Claude가 새로 Notion 페이지를 만들 때는 **매번 사용자가 지정하는 부모 페이지 아래에** 만든다. 이전에 어디에 만들었는지를 기준으로 임의로 같은 위치를 재사용하거나, 최상위/다른 위치에 임의로 만들지 않는다 — 매번 확인한다.

## 3. 작업 시작 전 절차

1. **`notion-fetch`로 현재 페이지 상태를 먼저 확인한다.** 무엇이 이미 있는지 파악하지 않고 바로 쓰지 않는다.
2. 페이지 구조가 아직 안 정해졌다면(예: 새로 만든 빈 페이지), **한 페이지에 섹션(헤딩)으로 다 쌓을지, 문서 종류별로 하위 페이지를 분리할지**를 사용자에게 먼저 확인한다. 프로젝트마다 다시 정할 수 있으니 이전 프로젝트 방식을 기본값으로 재사용하지 않는다.
3. 구조가 확정되면, 아래 4절의 규격에 맞춰 승인된 위치에만 작성한다.

## 4. 표준 문서 규격

**이 절은 PM 기획 문서(제품·실험을 만드는 프로젝트)를 갖는 프로젝트에만 적용된다** — 순수 연구·스터디 저장소(예: DL 논문 재현, 알고리즘 학습용 프로젝트)처럼 "제품"이라는 개념 자체가 없는 프로젝트에서는 이 절이 정의하는 문서 세트(원페이저·PRD·TRD 등)가 대부분 무의미하다(`git-workflow.md` 2절 "조건부 이식" 참고). 이 문서의 나머지 절(1~3·5~8절 — 하위 페이지 관리, 시각화, 하네스 기록 페이지 등)은 그런 프로젝트도 Notion으로 진행상황을 관리한다면 그대로 유용하다.

프로젝트 성격에 따라 가감하되, 기본 순서는 이렇다 (모든 프로젝트에 전부 필요한 건 아니며, 실험/AB테스트가 없는 프로젝트라면 5번은 생략 가능):

1. **원페이저** — 문제 정의, 왜 중요한지, 아이디어, 기대 효과를 반 페이지 내외로. 본격 착수 전 pitch 문서.
2. **PRD (제품 요구사항 문서)** — 문제, 목표, 범위(한계 명시 포함), 로드맵. "무엇을·왜"를 다루고 "어떻게(기술적으로)"는 다루지 않는다 — 그건 아래 3번(TRD) 몫이다.
3. **TRD (기술 요구사항 문서, 2026-08-27 신설)** — PRD가 정한 "무엇을"을 "어떻게" 만들지에 대한 기술적 결정을 한곳에 모은다: 기술 스택·배포 대상, 서버/API 아키텍처(있다면), 데이터 모델·함수 계약(입출력 정의), 랜덤화·알고리즘 설계, 환경 세팅·재현 절차, 보안/시크릿 관리 원칙, 비기능 요구사항(성능·확장성 등). **ML/DL 파이프라인 전용 재현 절차(conda 환경, 랜덤 시드, 노트북 실행 순서 등)는 TRD가 아니라 `ml-project-workflow.md` 11절 "재현성 가이드" 몫이다** — TRD는 그 파이프라인에 국한되지 않는 프로젝트 전체 기술 결정(서버 아키텍처 등)을 다룬다. **PRD 직후 착수한다** — 이후 문서(성공지표트리·실험설계서·기능정의서 등)가 이 기술 결정을 전제로 쓰이기 때문이다. **버그·이슈 이력은 TRD가 아니라 별도 이슈 로그(이 하네스에서는 `docs/harness/bug-log.md`)가 담당한다** — TRD는 착수 전 기술 결정을 사전에 확정하는 문서이지, 구현 중 발견한 문제를 사후에 기록하는 문서가 아니다. 소규모 파일럿이라 기술 결정이 몇 개 안 되면, 별도 문서로 안 만들고 실험설계서·기능정의서 같은 관련 문서 안에 나눠 적어도 된다 — 다만 그 경우에도 "이 프로젝트는 TRD를 별도로 안 두고 O·O 문서에 나눠 적었다"는 걸 어딘가(예: PRD의 "다루는 것/안 다루는 것" 콜아웃)에 명시해, 나중에 "TRD가 어디 있냐"고 찾다가 못 찾는 일이 없게 한다.
4. **성공지표 트리** — North Star 지표 → 중간 동인 → 이번 작업이 직접 재는 지표 → 가드레일 지표(나빠지면 안 되는 것들).
5. **실험 설계서** (A/B 테스트 등 실험이 있는 경우) — 가설, 변형(A/B) 내용, 표본 크기·검정력, 랜덤화 방식, 분석 방법을 **실행 전에 미리 확정**해서 기록 (사후에 유리한 방법으로 바꾸지 않기 위함).
6. **기능정의서/화면정의서** — 실제 서비스용이 아니어도(프로토타입·테스트용이어도) 화면/기능을 최소한으로 정의. 프로덕션 수준으로 무겁게 쓸 필요는 없음. 화면정의서는 표준 순서를 따른다: **화면 목록 표**(화면ID/화면명/보이는 조건/대응 요구사항ID) → **화면별 상세**(각 화면마다 먼저 **저충실도 와이어프레임**을 텍스트 박스로 스케치한 뒤 — 요소 배치·순서만 보여주고 색상·폰트·간격 등 실제 시각 디자인은 다루지 않는다, 그건 별도 UI/UX 디자인 단계 몫이다 — 그 아래 **구성요소 표**: 요소/사용자 동작/호출 API/성공 시/실패 시) → **화면 전이도**(어떤 조건에서 어떤 화면으로 넘어가는지) → **공통 규칙**(에러 표시 방식, 이중 제출 방지 등 화면마다 반복 쓰지 않고 한 번에 모아두는 cross-cutting 규칙). 와이어프레임 없이 구성요소 표만 나열하면 "화면에 뭐가 있는지"는 알아도 "그것들이 어떻게 배치되는지"가 안 보여, 문서 이름이 "화면정의서"인데 실제로는 화면을 정의하지 못하는 문제가 생긴다.
   - **AB테스트/실험용 참여자 앱의 화면정의서를 쓰기 시작하는 시점이면, 착수 전에 `docs/harness/ab-test-app-workflow.md`에 따라 구현 방식(Streamlit/순수 HTML·CSS·JS/하이브리드)을 이미 확인했어야 한다** — 방식에 따라 아래 화면별 상세·구성요소 표에 담을 내용(컴포넌트 구조, 상태 관리 방식)이 달라지므로, 이 확인이 빠진 채로 화면정의서를 쓰기 시작하지 않는다.
   - **AB테스트/실험용 앱이라면 화면 목록에 참여자용 화면뿐 아니라 결과 확인용 백오피스(관리자용 결과 대시보드) 화면도 반드시 포함한다** — 참여자 응답이 쌓이는 대로 검정 결과(이항검정·신뢰구간 등)를 쉽게 확인할 수 있는 화면이 없으면, 결과를 볼 때마다 노트북/스크립트를 직접 열어야 해서 진행 상황 파악이 번거로워진다. **그 백오피스가 통계 검정 결과를 실시간에 가깝게 보여주는 경우, 화면 설계·시각 QA 판단 기준은 `docs/harness/stats-dashboard-design-reference.md`를 먼저 참고한다** — 단순 CRUD·조회용 백오피스라면 해당하지 않는다. 화면 설계 초안 때 참여자용만 떠올리고 관리자용을 빠뜨리기 쉬우므로, 화면 목록 표를 만들 때부터 "참여자용"과 "관리자용" 두 부류가 있는지 스스로 점검한다. 이와 별개로, 로그를 직접 읽어 분석하는 스크립트/노트북도 표준 산출물로 함께 둔다(`ml-project-workflow.md` 5절 "모델만 저장하지 않는다"·11절 재현성 가이드 원칙과 같은 정신 — 백오피스가 있어도 원자료를 직접 재현·검증할 수 있는 경로는 따로 유지한다).
     - **백오피스 규모가 커지면 참여자용 문서와 아예 별도 문서 세트로 분리한다** — 사용자(고객 vs 운영자), 기능 성격(참여자 흐름 vs CRUD·권한 관리·통계), 인증·권한 체계(참여자 앱은 무인증인 경우가 많은 반면 백오피스는 역할별 접근 제어가 필요)가 서로 다르면 한 문서 안에 섞을수록 오히려 구조가 흐려진다. 판단 기준: 백오피스 화면이 결과 대시보드 1~2개 수준이면 참여자용 화면정의서 안에 같이 둬도 충분하지만, 화면 수가 여럿이거나 역할별 권한·별도 로그인이 필요해지면 `06b_백오피스_기능정의서_화면정의서`처럼 별도 파일·별도 Notion 하위 페이지로 뗀다. 애매하면 먼저 사용자에게 분리 여부를 확인한다.
7. **리스크 체크리스트** — 미리 예상되는 실패/오염 요인을 짧게 나열.
8. **결과 보고서** (실행 후) — 수치 해석 + go/no-go 같은 의사결정 추천까지 포함.
9. **회고** (실행 후) — 잘된 것/안된 것/다음 단계.

### 4-1. 로컬 초안 → Notion 반영 → 버전업 워크플로우

위 문서들은 Notion에 바로 쓰지 않고 다음 순서를 따른다:

0. **데스크리서치(먼저, 승인 없이 자율 수행)**: 각 문서를 쓰기 전에 근거를 조사한다 — **내부**(과제 스펙, 기존 Notion 기록, 하네스 문서)와 **외부**(웹 검색으로 찾은 실무 사례, 관련 연구·아티클, 유사 제품 패턴) 둘 다 포함. 조사 자체는 사용자 확인 없이 바로 진행하되, 그 결과로 실제 문서를 새로 쓰는 "실행" 단계는 별도로 승인받는다.
1. **로컬에 초안 작성**: `docs/planning/`에 마크다운으로 초안을 쓴다(예: `01_원페이저_v1.0.md`). 0번 데스크리서치 결과를 근거로 채운다.
2. **오타·AI 티 점검(Notion에 올리기 전 필수, 생략 불가)**: 로컬 초안을 처음부터 끝까지 다시 읽으며 (a) 오타·맞춤법·조사 오류, (b) "AI 티"(상투적 어구, 기계적으로 균일한 문장 길이, 과잉 구조화, 근거 없는 헤징, 스마트따옴표/em dash 남용 등)를 점검한다 — 체크리스트는 `docs/harness/report-writer-contract.md`의 "최종 QA 단계 (3) AI 티 제거"를 그대로 적용한다(장르가 달라도 같은 문제이므로 중복 정의하지 않는다). Notion에 옮긴 뒤에도 같은 점검을 한 번 더 한다 — Notion 서식 변환 과정에서 새로운 오류(예: HTML 태그 leak, 4-3절 참고)가 생길 수 있기 때문이다.
3. **Notion에 복사 — 문서마다 별도 하위 페이지로**: 메인 페이지 본문에 섞어 넣지 않는다. 기획 문서 각각을 **독립된 하위 페이지**로 만들고, 메인 페이지엔 "기획 문서" 같은 전용 섹션에 그 하위 페이지 링크만 모아둔다(2절 원칙대로 위치는 매번 확인).
   - **제목 형식**: `{번호}_{서비스/실험명}_{문서유형}_v{버전}` (예: `01_가격UX_원페이저_v1.0`). 로컬 파일명과 번호·버전을 맞춰서 서로 대응이 바로 보이게 한다. **제목 텍스트 맨 앞에 이모지를 직접 타이핑해 넣지 않는다** — 문서 유형을 한눈에 구분하고 싶으면 `notion-update-page`의 `icon` 파라미터로 페이지 고유 아이콘을 설정한다(Notion이 제목 옆에 별도로 렌더링). 제목 문자열에 이모지를 같이 넣으면, 페이지 아이콘(예: 🧪)과 제목 속 이모지(예: 🧪 05_...)가 나란히 겹쳐 보이는 중복 렌더링 버그가 생긴다(2026-08-24 실사고 — `notion-update-page`로 버전 번호만 바꾸려다 제목에 이모지가 이미 두 번 박혀 있던 걸 뒤늦게 발견, `icon` 파라미터로 이미 정상 설정돼 있었는데도 제목에 또 넣은 것이 원인). 제목을 갱신할 때마다 이 문제가 없는지(제목 앞에 이모지 문자가 있는지) 확인하고, 있으면 제거한다 — 아이콘은 `icon` 파라미터가 전담한다.
   - **색상 구분**: 하위 페이지 링크마다 문서 유형별로 다른 배경색을 지정해(`<page color="...">`) 목록만 훑어도 어떤 유형인지 바로 구분되게 한다. 이 프로젝트 배정(진행보드 실제 번호 기준, 2026-08-22 갱신): 00 데스크리서치=orange_bg, 01 원페이저=blue_bg, 03 PRD=gray_bg, 04 성공지표트리=green_bg, 05 실험설계서=purple_bg, 06 기능정의서/화면정의서=pink_bg, 07 리스크체크리스트=red_bg, 22 결과보고서=yellow_bg, 23 회고=brown_bg. 02는 문서가 아니라 진행보드 실행계획 항목("A/B 내용 확정")이라 색 배정 대상이 아니다.
     - **색상 규칙 정정(2026-08-26) — "페이지 전체에서 완전히 유일해야 한다"가 아니라 "같은 리스트 안에서 바로 위아래(인접) 항목과 안 겹치면 된다".** Notion 배경색은 9종(orange/blue/gray/green/purple/pink/red/yellow/brown)뿐이라 PM 문서 9종이 이미 전부 소진했다 — 전체 유일성을 요구하면 그 이후 생기는 어떤 문서 유형도 색을 못 받는다. 대신 그 문서가 실제로 나열되는 리스트(예: "ML 전용 문서" 표 아래 목록) 안에서 바로 인접한 항목들과만 겹치지 않으면 된다 — 페이지의 다른 섹션(예: "기획 문서" 리스트)에 있는 문서와 우연히 같은 색이어도, 서로 다른 리스트라 같이 스캔될 일이 없으므로 혼동을 안 일으킨다. **08~11(ML 문서)도 이제 무색이 아니라 이 규칙대로 색을 배정한다** — 과거의 "ML/DL 문서는 무색" 기본값(`ml-project-workflow.md` 11절)은 이 정정으로 폐기됐다.
     - **적용 사례(2026-08-26)**: 17번(ML 모델카드)에 사용자가 Notion 앱에서 직접 `pink_bg`를 배정했다 — 06번(기획 문서 리스트)과 같은 색이지만 17번이 실제로 나열되는 "ML 전용 문서" 리스트의 인접 항목(08=yellow_bg·09=brown_bg·10=blue_bg·11=green_bg)과는 겹치지 않아 위 규칙을 만족한다. 앞으로 이 프로젝트의 어떤 자동화(`planning-doc-qa` 등)도 이런 "다른 리스트와의" 색 중복을 실수로 보고 재조정하지 않는다.
4. **사용자가 Notion에서 직접 다듬는다**: 사용자가 Notion 페이지에서 검토·수정하며 완성도를 높인다 — 이 단계의 실제 편집은 사용자 몫이다.
5. **버전업**: 내용이 실질적으로 바뀔 때마다 로컬 파일도 버전을 올린다 — 파일명에 버전을 명시하고(`_v1.0.md` → `_v1.1.md`), 구버전은 `docs/planning/old/`로 옮겨 보존한다(삭제하지 않음). Notion 쪽 하위 페이지 제목의 버전 표기와 본문 내용도 최신으로 갱신한다. 버전을 올릴 때도 2번 점검을 다시 거친다.
   - **버전 기록(changelog)은 접이식 토글로 감싼다** — 문서 맨 위에 `> **vX.X**: ...` 인용구 줄이 버전마다 계속 쌓이면, 정작 봐야 할 본문 내용보다 이력이 먼저 눈에 들어와 가독성을 해친다. 로컬 `.md`는 `<details><summary>버전 기록</summary>` ... `</details>`(GFM 표준, 기본 접힌 상태로 렌더링됨)로 감싸고, Notion은 같은 태그(`<details><summary>버전 기록</summary>` 안에 자식 블록을 들여쓰기)의 토글 블록으로 반영한다 — 이 문법은 `notion://docs/enhanced-markdown-spec`의 "Toggle" 절을 직접 조회해 확인한 것이다(2026-08-22). 앞으로 이 규칙을 적용할 때 문법이 의심되면 이 문서 문구를 추측으로 베끼지 말고 그 스펙을 다시 조회해서 재확인한다.
   - **"버전 기록" 토글 안은 평문이 아니라 버전별 하위 토글 목록으로 만든다** — 바깥 토글 하나에 모든 버전을 텍스트로 죽 나열하면 결국 다시 긴 문단이 된다. 바깥 "버전 기록" 토글 안에, 버전마다 별도의 하위 토글(`**vX.X (YYYY-MM-DD)**`를 summary로)을 만들고 그 설명은 하위 토글 안에 넣는다 — 읽는 사람이 궁금한 특정 버전만 펼쳐보고 나머지는 접어둘 수 있게 한다. 로컬 `.md`(GFM)와 Notion 둘 다 `<details>` 태그는 중첩(nesting)을 지원하므로, 바깥 `<details><summary>버전 기록</summary>` 안에 버전 수만큼 `<details><summary>vX.X (YYYY-MM-DD)</summary>...내용...</details>`를 들여쓰기해서 넣는다.
   - **날짜는 실제 시점을 쓴다** — 새로 버전을 올릴 때는 그 시점의 실제 날짜를 쓴다. 과거에 이미 날짜 없이 적힌 버전 항목을 소급 보완할 때는 추측하지 않고 `git log --follow --diff-filter=A -- <파일경로>`나 해당 버전이 처음 등장한 커밋을 `git log -p`로 찾아 실제 커밋 날짜를 그대로 쓴다.
   - **정렬 순서는 최신 버전이 맨 위다** — 하위 토글을 위에서 아래로 최신 → 차순 → ... 순으로 놓는다(예: v1.3 → v1.2 → v1.1, 오래된 순으로 쌓지 않는다). 가장 최근 변경이 뭔지 바로 보이는 게 우선이다.
   - **이 토글은 v1.0(최초 작성) 시점부터 만든다** — "버전이 2개 이상 쌓이면 그때 토글로 정리한다"처럼 나중으로 미루지 않는다. 처음 문서를 쓸 때부터 바깥 "버전 기록" 토글을 만들고, 그 안에 위 형식 그대로 하위 토글 하나(`**v1.0 (YYYY-MM-DD)**`를 summary로, 핵심 내용은 그 안에)를 넣어둔다 — 평문으로 넣지 않는다(바로 위 불릿들과 동일 규칙). 그래야 나중에 버전이 올라갈 때마다 이미 있는 바깥 토글 안에 하위 토글만 하나씩 추가하면 되고, "지금부터 토글 구조로 바꿔야지"라며 뒤늦게 기존 인용구를 옮기는 작업이 생기지 않는다.
   - **정합성 체크(교차 참조 갱신)**: 이번 버전업이 이전 결정을 뒤집거나 수정하는 내용이라면, 그 이전 결정이 인용·요약된 다른 곳(다른 계획 문서, Notion 메인 페이지의 표·콜아웃 등)이 있는지 찾아 함께 갱신한다 — 버전업한 문서 본문만 고치고 그 결정을 참조하던 다른 자리를 그대로 두면, 서로 다른 결정이 동시에 존재하는 것처럼 보여 나중에 어느 쪽이 최신인지 헷갈리게 된다. Notion 메인 페이지 콘텐츠를 갱신 대상에 포함하는 것은 1절 예외("Claude가 만들어서 계속 갱신하기로 명시한 페이지/섹션")에 해당하는 콘텐츠에 한한다 — 사용자가 직접 쓴 원문까지 이 명목으로 고치지 않는다. 구체적 사건 경위는 이 포터블 문서 대신 8절 원칙대로 Notion 하네스 기록 페이지에 남긴다.
6. **최종 시각화**: 완성되면 표·Mermaid 다이어그램 등으로 한눈에 보이게 정리한다(6절 참고).

**이 점검은 Notion 문서에만 한정되지 않는다** — 메인 페이지(카탈로그성 상시 갱신 내용 포함) 등 Claude가 직접 쓰거나 고치는 모든 Notion 콘텐츠에 동일하게 적용한다.

`docs/planning/`은 이 프로젝트가 실제로 작성한 기획 문서 원본이라 **이식 대상이 아니다**(`git-workflow.md` 2절 "이식 대상 아님" 목록 참고) — `docs/harness/`(재사용 가능한 절차)와 성격이 다르다.

### 4-2. 문서 작성 스타일 — 명목화 요약 먼저, 설명은 그 아래

주저리주저리 풀어쓰지 않는다. `docs/planning/`의 문서든 Notion 본문이든, 섹션·문단은 다음 순서를 따른다:

1. **첫 줄: 핵심을 한 문장으로 명목화·요약**(굵게) — 결론·핵심 주장을 먼저 던진다.
2. **그 아래: 근거·설명**을 문단으로 풀어쓴다.

예시:
- **지양**: "AI가 중고거래 상품의 적정 가격을 예측해줄 때, 그 결과를 판매자에게 어떻게 보여줘야 신뢰를 얻을 수 있는가? 지금까지 이 질문에 답한 국내 사례는 사실상 하나뿐이다 — 당근마켓만..."(질문으로 시작해서 한참 돌아 핵심에 도달)
- **권장**: "**당근마켓만 유일하게 AI 가격을 제안하고, 그마저도 범위 형태다.** 국내 4대 중고거래 플랫폼을 확인한 결과, AI가 실제로 가격을 제안하는 곳은 당근마켓뿐이며..."(결론을 먼저 던지고 그 다음에 풀어씀)

`docs/harness/report-writer-contract.md`의 "강조 문장 패턴"(표·차트 직후 핵심 요약 한 문장)과 같은 원칙이지만 적용 범위가 더 넓다 — 표 뒤뿐 아니라 **모든 섹션·문단의 서두**에 적용한다.

**명목화 규칙은 "짧게 쓴다"가 아니라 "먼저 결론을 던지고 그 아래를 풀어쓴다"는 뜻이다** — 첫 줄이 결론이면 그 아래 설명 문단 자체는 길어도 된다. 위반의 실제 패턴은 결론 없이 조건·예외·부연을 한 문장 안에 계속 이어붙이는 것이다(예: "A면 B고, 다만 C인 경우엔 D이며, 그런데 E일 때는..."). 이런 문장을 발견하면 먼저 "그래서 결론이 뭔가"를 한 문장으로 뽑아 맨 앞에 굵게 세우고, 나머지 조건·예외는 그 아래 불릿이나 문장으로 풀어낸다.

**Notion 본문에서는 Claude가 조사·작성한 설명을 회색으로 비강조 처리한다(이 규칙은 Notion 전용이다 — 로컬 `.md`는 대상 아님, GFM 등 표준 마크다운 렌더러에 `<span>`을 그대로 쓰면 서식 없이 원문 태그가 노출된다).** 사용자가 직접 쓰거나 확정한 내용과, Claude가 자율적으로 조사·설명해서 덧붙인 내용을 시각적으로 구분해, 나중에 다시 읽을 때 "이건 내가 직접 판단한 것"과 "이건 Claude가 조사해서 채워준 배경 설명"을 한눈에 알아볼 수 있게 한다.

- Claude가 자율적으로 조사·요약해서 추가한 설명·맥락 문단은 `<span color="gray">텍스트</span>`로 감싼다 — 이 문법은 `notion://docs/enhanced-markdown-spec`의 "Inline colors" 절을 직접 조회해 확인한 것이다(2026-08-22). 이 `gray`는 **텍스트 전경색**이며, 4-1절 색상 팔레트의 `gray_bg`(문서 유형 배경색, 03_PRD에 배정됨)와는 다른 값이다 — 서로 다른 용도라 겹치거나 충돌하지 않는다.
- 사용자가 직접 쓴 문장, 사용자와 함께 확정한 결정 사항(콜아웃·굵게 강조 등 기존 서식)은 색을 넣지 않고 그대로 둔다 — 회색 처리 대상이 아니다.
- 헷갈리면(이게 Claude 단독 조사 내용인지, 사용자와 논의해서 확정한 결정인지 애매하면) 회색 처리하지 않는다 — 과도하게 회색을 남발하면 오히려 뭐가 중요한 결정인지 구분이 흐려진다.
- **같은 목록 중간에 끼워 넣지 않는다** — 목록(불릿) 안에 회색 항목이 일반 항목들 사이에 섞이면 읽는 흐름이 끊긴다. 회색 처리할 항목은 그 목록의 맨 끝으로 옮긴다.

### 4-3. Notion 본문에 굵게·강조를 넣을 땐 마크다운만 쓴다 — HTML 태그 금지

**표 셀 등 아무 데서나 `<strong>`처럼 HTML 태그를 쓰면 렌더링 안 되고 글자 그대로 노출(leak)된다.** Notion API는 본문 텍스트를 마크다운으로 파싱하며 `<strong>`·`<b>`·`<em>` 같은 raw HTML 태그는 서식으로 해석하지 않고 그냥 문자 그대로 저장·표시한다 — 특히 `<table>`/`<tr>`/`<td>` 태그로 직접 표를 쓸 때, "이 안에선 마크다운이 안 먹으니 HTML로 강조해야겠다"고 착각하기 쉬운데 이것도 틀렸다: 표 셀 안에서도 굵게는 그대로 `**텍스트**`를 쓴다.

- **어디서든 강조는 `**텍스트**`(마크다운)만 쓴다** — 표 셀 안이든 밖이든 예외 없음.
- **`<`·`>`·`&` 같은 기호를 HTML 엔티티(`&lt;`, `&gt;`, `&amp;`)로 이스케이프해서 쓰지 않는다 — 그대로 노출된다.** "표 안이라 `<`를 못 쓰니 `&lt;`로 이스케이프해야겠다"는 것도 HTML 태그 착각과 같은 종류의 실수다 — Notion은 이 엔티티를 디코딩하지 않고 문자 그대로 저장해 `p&lt;0.05`처럼 화면에 그대로 보인다. `<`·`>`·`&`가 필요하면 이스케이프 없이 그 문자를 그대로 쓴다(예: `p < 0.05`).
- `<table>`/`<tr>`/`<td>`, `<page url="...">`, `<database url="...">`, `<callout>`, `<details>`/`<summary>`(토글), `<span color="...">`(인라인 색상, 4-2절 회색 비강조 규칙에서 씀)처럼 Notion 마크다운이 자체적으로 지원하는 **구조 태그**는 그대로 써도 된다 — 여기서 금지하는 건 그 구조 태그 *안의 텍스트 서식*(굵게·기울임 등)을 HTML로 쓰는 것뿐이다.
- `update_content`/`create_pages`로 표를 작성·수정한 뒤에는 **반드시 `notion-fetch`로 다시 읽어 실제 렌더링 결과를 확인**한다 — 호출이 에러 없이 성공했다고 해서 의도한 서식대로 보인다는 보장이 없다.
- **굵게(`**텍스트**`)를 인라인 코드(`` `코드` ``) 위에 걸쳐서 쓰지 않는다** — `**...앞부분 `코드` 뒷부분...**`처럼 하나의 굵게 안에 코드 스팬이 끼면, 재조회 시 `****코드****`처럼 별표가 겹쳐 보이는 서식 깨짐이 생긴다. 코드 스팬 앞에서 굵게를 닫고, 필요하면 코드 스팬 뒤에서 새로 연다.
- **한글을 `\uXXXX` 유니코드 이스케이프로 손수 계산해서 타이핑하지 않는다 — 오타가 계속 났다.** 표 셀 안 등 이스케이프가 필요해 보이는 상황이라도, 도구 호출 파라미터에 한글 글자를 있는 그대로(리터럴 UTF-8) 적는다. 한 글자씩 코드포인트로 변환해 넣으면 자모가 미묘하게 틀린 다른 글자가 되기 쉽고("끊기지"→"끓기지", "쏠림"→"쓸림", "카카오톡"→"카카오톱" 등 다수 발생), 겉보기엔 그럴듯해서 스스로도 못 알아채고 넘어가기 쉽다 — 반드시 수정 직후 `notion-fetch`로 재확인한다(위 항목과 같은 이유, 특히 이 실수엔 더 중요). **같은 단어의 오타 수정이 "no matches found"로 두 번 이상 실패하면, 세 번째도 같은 방식(그 단어만 다시 손으로 입력)으로 재시도하지 않는다** — 실패할 때마다 오류 메시지가 되돌려주는 "찾으려 한 문자열"을 그대로 다음 old_str로 복사해 재사용하거나(직접 타이핑을 아예 안 거치므로 오타가 재발할 수 없음), 그래도 안 되면 `notion-update-page`를 `command: "update_content"`(부분 교체) 대신 `command: "replace_content"`(본문 전체를 새 내용으로 통째로 교체)로 바꿔 그 페이지를 다시 쓰는 쪽으로 전환한다 — 같은 도구의 다른 모드일 뿐이라 부분 매칭 실패 자체가 발생하지 않는다.

### 4-4. 문서 상단엔 메타 표 + 콜아웃, 맨 끝엔 근거 절을 둔다

**제목만 있고 그 문서의 성격·경계가 안 적혀 있으면, 다음 문서를 쓸 때 앞 문서와 내용이 겹치거나 빠지는 걸 놓치기 쉽다.** PM 문서(원페이저 이후 전부)는 본문 시작 전·끝에 세 가지를 둔다:
- **메타 표**: 문서유형 / 버전 / 상태(초안·Baseline 확정 등)를 짧은 표로.
- **"이 문서가 다루는 것 / 안 다루는 것" 콜아웃**: 이 문서의 책임 범위를 한두 문장씩 명시한다(예: "PRD는 무엇을·왜 만드는지를 다루고, 어떻게 구현할지는 화면정의서·기능정의서 몫이다"). 이렇게 적어두면 다음 문서를 쓸 때 이 문서 영역을 침범하는지, 반대로 빠뜨린 영역이 있는지 스스로 점검할 기준이 생긴다.
  - **"안 다루는 것"은 빠짐없이 나열하고, 각 항목마다 정확히 어느 문서·어느 절이 담당인지 짚는다** — "다른 문서에 있다"고 뭉뚱그리지 않는다. 특히 놓치기 쉬운 범주: 개발 환경 세팅(Python 버전, conda/venv 등 — 재현성가이드·`CLAUDE.md` 몫), 구체적 구현 방식(랜덤화 알고리즘 등 — 실험설계서 몫), 화면 UI 상세(화면정의서 몫). 이 목록이 불완전하면, 문서 기반으로 협업하는 사람(다른 팀원 등)이 "이 정보가 어디 있는지" 문서만 봐서는 못 찾고 매번 물어봐야 하는 상황이 생긴다 — PRD 자체에 그 세부까지 옮겨 적으라는 뜻이 아니라, PRD가 정확한 이정표 역할을 하게 만든다는 뜻이다.
- **"근거" 절(문서 맨 끝)**: 이 문서의 주장·수치가 어디서 왔는지 인용 목록을 남긴다 — 다른 계획 문서(버전까지 명시), 외부 자료, 직접 실행한 검증 스크립트 등. 근거 없이 쓰인 주장인지, 어느 문서를 봐야 재확인할 수 있는지를 나중에 추적할 수 있게 한다. **버전이 여러 번 올라가는 문서(모델카드 등)는 이 절에 "vX.X에서는 ~를 확인했다"는 식의 프로즈 문단이 버전마다 계속 덧붙어 쌓이기 쉽다 — 문단이 3개 이상 누적되면 표로 재구조화한다**(열 예시: 버전 | 확인한 주장/수치 | 근거 파일·셀 | 확인 방법). 6절의 "표·다이어그램 우선" 원칙과 4-2절의 명목화 원칙이 근거 절에도 그대로 적용된다는 뜻이다 — 근거 절이라고 프로즈 누적을 예외로 두지 않는다.

### 4-5. ID 체계로 문서 간 추적성을 만든다

**요구사항·화면·기능이 서로 다른 문서에 흩어져 있으면, "이 화면이 어느 요구사항 때문에 있는지"를 나중에 되짚기 어렵다.** 접두사+번호로 각 산출물에 ID를 붙이고, 문서 간 대응을 표로 연결한다:
- **요구사항**: `FR-01`, `FR-02`... (PRD의 "범위(포함)" 목록 등)
- **화면**: `SCR-001`, `SCR-002`...(화면정의서)
- **기능**: `FN-001`, `FN-002`...(기능정의서)
- **유스케이스**: `UC-01`...(필요할 때만 — 흐름이 단순한 프로젝트는 생략 가능)
- **인수 기준(완료 조건)**: `AC-01`...(PRD의 "완료 기준"/체크리스트 등) — 제3자가 그대로 보고 통과/실패를 판정할 수 있는 문장으로 쓴다("정상 동작한다"처럼 판단자 재량이 들어가는 표현은 피한다).

화면정의서·기능정의서 마지막 절에는 이 ID들을 서로 잇는 **매핑 표**(예: FN-xxx ↔ FR-xx ↔ SCR-xxx)를 둔다 — PRD 하나만 봐서는 안 보이던 "이 요구사항이 실제로 어느 화면·어느 함수로 구현됐는지"가 매핑 표 하나로 추적 가능해진다.

## 5. 하위 페이지·데이터베이스를 적극 활용한다

메인 페이지에 모든 내용을 계속 쌓기만 하면 나중에 한눈에 훑어보기 어려워진다. 다음 기준으로 구조를 나눈다.

본문 흐름에서 벗어난 부수적·상세한 내용(예: 실험 원자료 로그, 세부 비교 결과 전체, 참고자료 모음)은 메인 페이지에 다 늘어놓지 않고, Notion 마크다운의 하위 페이지 문법(`<page url="..." >제목</page>`)으로 별도 페이지를 만들어 링크만 남긴다. 메인 페이지는 한눈에 훑을 수 있는 요약 수준을 유지한다.

**`<page url="...">` 태그는 단순 링크가 아니라 워크스페이스 계층의 부모-자식 소유권 그 자체다 — content에서 이 태그를 제거하면 그 하위 페이지가 실제로 archive(휴지통)로 들어갈 수 있다.** `notion-create-pages`로 부모=현재 페이지에 하위 페이지를 만들면, Notion이 그 `<page>` 블록을 현재 페이지 맨 끝에 자동으로 붙이는데, 이 위치가 원하는 섹션(예: "기획 문서")이 아닌 경우가 흔하다.

**⚠️ 과거에 이 절이 "1차 호출(제거+재삽입)로 같은 update_content 안에서 안전하게 옮길 수 있다(확인됨)"고 적어뒀던 절차는 틀렸다 — 실제로 실행했더니 그 하위 페이지가 archive(휴지통)로 들어갔다(2026-08-22 실사고, 되돌리는 도구가 없어 새 페이지로 다시 만들어야 했다).** "같은 호출 안에서 제거와 재삽입을 함께 보낸다"는 이론과 달리, 실제로는 제거 쪽이 삭제로 처리되는 경우가 있다는 뜻이다 — content 편집으로 기존 `<page>` 블록을 옮기는 시도 자체를 하지 않는다.

- **위치를 옮겨야 하면 사용자에게 Notion 앱에서 직접 드래그로 옮겨달라고 요청한다** — API/content 편집으로는 안전하게 재현되지 않는다는 게 실증됐다.
- **원하는 자리에 링크만 보이면 충분하면 `<mention-page url="...">`를 그 자리에 추가한다** — 순수 인라인 참조라 소유권과 무관해 항상 안전하고, 자동 삽입된 원래 위치의 `<page>` 태그는 그대로 둔다(제거하지 않는다). 완전히 그 자리로 옮겨진 것처럼 보이진 않지만(원래 위치에도 페이지가 남음), 삭제 위험 없이 원하는 곳에서 바로 열어볼 수 있다.
  - **단, 4-1절의 표준 문서 카탈로그(이 프로젝트에서는 00~11·17번 — 실제 번호는 프로젝트마다 다르다. 표 아래 `<page url="..." color="...">` 목록이 줄지어 있는 자리)에 새 문서를 추가할 때는 이 mention-page 대체를 기본값으로 쓰지 않는다.** 이 카탈로그는 형제 문서들이 전부 실제 페이지 카드(색상 포함)로 나란히 보이는 자리라, 그중 하나만 mention(단순 링크 텍스트)으로 대체되면 시각적으로 눈에 띄게 어긋나 보인다 — "링크만 있으면 충분한" 경우가 아니다. 이런 자리에서는 항상 위 방법(사용자에게 드래그 요청)을 먼저 쓰고, mention은 사용자가 명시적으로 "링크만 있어도 된다"고 확인해준 경우에만 예외로 쓴다. (2026-08-27 실사고 — `planning-doc-qa`가 17번 모델카드를 이 판단 없이 mention으로 때웠다가 사용자가 "리스트로 있어야할 곳"이라고 지적함.)
- **하위 페이지의 부모(소유권) 자체를 바꿔야 하면** `notion-move-pages` 도구를 쓴다 — 이건 content의 `<page>` 태그를 건드리지 않고 워크스페이스 계층만 바꾸는 별도 API라 안전하다. 다만 이 도구는 "부모가 누구인지"만 바꿀 뿐, 부모 페이지 **본문 안에서 그 하위 페이지 링크가 정확히 어느 줄에 나타나는지**(content 내 위치)까지 옮겨주진 않는다 — 그건 여전히 위 두 방법(사용자 직접 이동, 또는 mention-page) 중 하나로 다룬다.

여러 항목을 반복적으로 추가·갱신하며 상태를 추적해야 하는 내용(예: 실험 결과 목록, 하이퍼파라미터 시도 기록처럼 계속 쌓이는 항목형 데이터)은 정적 표보다 Notion 데이터베이스(속성: 상태·날짜·담당 등)로 만들어서 필터·정렬·보기 전환이 가능하게 한다. 단, 4절의 "리스크 체크리스트"처럼 이미 표준 문서 항목으로 정의된 것은 그 문서 형태를 우선하고, 여기서 말하는 데이터베이스화는 그 문서 안의 개별 리스크 항목이 계속 늘어나 추적이 필요해질 때만 고려한다 — 같은 대상을 문서로도 만들고 DB로도 또 만드는 중복을 피한다.

판단 기준은 이렇다: 나중에 다시 찾아보거나 상태를 추적해야 하는 반복적 항목이면 데이터베이스로, 본문 흐름에서 벗어난 상세·부가 정보면 하위 페이지로, 지금 바로 훑어봐야 할 핵심 요약이면 메인 페이지에 그대로 둔다.

새 하위 페이지·데이터베이스를 만들 때도 2절(새 페이지는 어디에 만들지)의 원칙을 그대로 따른다 — 위치를 임의로 정하지 않고 확인한다. 이미 메인 페이지에 있는 기존 내용을 하위 페이지/데이터베이스로 옮기는 건 "기존 내용 수정"에 해당하므로, 1절의 절대 규칙대로 사용자 확인 없이 임의로 재구성하지 않는다 — 이관은 매번 먼저 제안하고 승인받는다.

**번호가 붙은 항목을 담는 데이터베이스의 기본(이름순) 정렬은 두 자리 이상 번호가 섞이는 순간 0-패딩 없이는 깨진다.** Notion의 텍스트 정렬은 문자열 비교라 "10."이 "2."보다 앞에 온다(자연 정렬이 아님) — 두 자리 이상 번호가 나올 가능성이 있는 목록(로드맵 단계 등)은 처음 만들 때부터 "00.", "01." 처럼 0-패딩된 이름을 쓴다. 이미 패딩 없이 만든 경우 뒤늦게 이름을 패딩 형태로 고치고 뷰의 정렬을 이름 오름차순으로 맞춘다.

**진행보드류 DB(칸반)는 상위 로드맵 다이어그램보다 더 세분화된 실행 단위로 채운다 — 로드맵을 그대로 복붙한 목록에 그치면 안 된다.** 로드맵(Mermaid 등)은 "무엇을 어떤 순서로 하는지" 큰 흐름을 보여주는 용도고, 진행보드는 사용자가 Claude와 매일 스텝을 맞춰가는 실무 투두 리스트라 목적이 다르다 — 로드맵의 항목 하나가 실제로는 여러 세션·여러 산출물에 걸치는 작업(예: "ML 모델링" 한 단계가 실제로는 EDA·전처리·모델비교·튜닝·최종확정 5개 노트북)이라면, 진행보드에는 그 세부 단위 각각을 별도 항목으로 넣는다.
- **새 항목을 기존 번호 체계 사이에 끼워 넣어야 할 때는 접두사(예: "ML-01.")나 서브번호(예: "07a.")보다 전체를 하나의 연속 번호로 재정렬하는 쪽을 기본으로 삼는다** — 재번호 자체는 각 항목의 이름 필드만 바꾸면 되므로 부담이 크지 않고, 접두사·서브번호는 기존 번호를 안 건드리는 대신 "지금 실제로 일할 순서"가 번호에 드러나지 않는다는 단점이 있다. 접두사는 재번호할 항목이 아주 많아 사용자가 명시적으로 "이번엔 접두사로 붙여줘"라고 할 때만 예외로 쓴다. 무엇을 얼마나 세분화할지는 애매하면 먼저 사용자에게 확인한다.
- 각 항목의 **"유형"** 같은 select 속성으로 워크스트림(기획 문서/ML 파이프라인/UI-UX/AB테스트/통계 및 분석/보고문서 등)을 칩으로 구분해두면, 번호가 연속이어도 시각적으로 구분할 수 있다 — 번호 체계와 유형 칩은 서로 다른 문제(정렬 vs 분류)를 풀므로 같이 쓴다. 유형은 multi_select로 만들어도 된다(한 항목이 "기획 문서"이면서 동시에 "AB테스트"인 것처럼 문서종류×워크스트림 두 축을 동시에 표현해야 할 때).
- **번호가 연속(00~24 등)이라고 해서 실행 순서까지 전부 순차인 건 아니다 — 서로 독립적인 트랙은 병렬로 착수할 수 있고, 이걸 놓치면 실제로 필요 없는 대기 시간이 생긴다.** 항목 수가 많고 여러 워크스트림이 뒤섞인 진행보드라면, "유형"과는 별도로 **"실행 트랙"**(또는 "병렬 그룹") 같은 select 속성을 하나 더 두고 각 항목을 트랙별로 태깅한다 — 같은 트랙 안에서는 순차(뒤 번호가 앞 번호 완료를 기다려야 함), 다른 트랙끼리는 그 트랙들의 공통 선행 조건(보통 첫 몇 개의 공용 문서)만 끝나면 병렬 착수가 가능하다는 뜻이다. "유형"은 그 항목이 *무엇에 관한 것인지*(문서종류×워크스트림) 분류하는 축이고, "실행 트랙"은 *언제 시작할 수 있는지*(스케줄링) 분류하는 축이라 목적이 다르다 — 유형이 이미 있다고 실행 트랙을 생략하지 않는다. 로드맵(Mermaid 등)에 그려둔 병렬 분기가 있다면 그 분기 구조를 그대로 트랙 이름으로 옮기면 되므로 새로 설계할 필요는 없다. 진행보드 DB 상단이나 근처에 "같은 트랙=순차, 다른 트랙=병렬 가능"이라는 범례를 한 줄 남겨서 이 트랙 칩이 유형 칩과 헷갈리지 않게 한다.
- **"이 항목은 어느 유형이야?" 같은 질문은 그 항목 하나에 대한 것으로 좁게 받아들인다** — 답을 찾았다고 해서 같은 논리를 다른 항목들에도 확대 적용해 한꺼번에 재태깅하지 않는다. 하나를 콕 집어 물어본 질문에 답하면서 비슷한 논리로 관련 없는 다른 항목들까지 함께 태깅해버리면, 사용자가 물어보지 않은 범위까지 임의로 건드린 셈이 된다. 여러 항목을 한 번에 재검토·재태깅하고 싶으면 사용자가 "전체 리스트 다시 체크해줘"처럼 범위를 명시할 때만 한다.
- **상태(시작 전/진행 중/완료) 값은 Claude가 실제 작업 진행에 맞춰 직접 갱신하되, "진행 중"과 "완료"는 갱신 시점이 다르다** — 그 항목에 실질적인 작업을 시작하면 곧바로 "진행 중"으로 바꾼다(사용자가 매번 수동으로 바꿀 필요 없음). 반면 "완료"는 Claude가 초안 작성·로컬 저장·Notion 반영을 마쳤다고 해서 자동으로 바꾸지 않는다 — 사용자가 검토 후 다음 스텝으로 넘어가자고 명시적으로 신호를 줘야 그때 "완료"로 바꾼다. 산출물이 다 나온 것과 사용자가 그 산출물을 승인한 것은 다른 사건이기 때문이다. 여러 항목에 걸친 작업이면 시작 시점에 관련된 모든 항목을 "진행 중"으로 한 번에 표시한다.
- **"완료"로 바뀌는 순간 그 항목의 날짜 속성에 완료 날짜를 함께 기입한다 — 날짜는 오직 "완료" 상태만을 뜻한다.** 이미 "완료"였던 항목이 다시 "진행 중"으로 되돌아가면(재작업 등) 날짜 값도 함께 지운다 — "완료된 적이 있다"는 이력이 아니라 "지금 완료 상태인가"만 나타내는 값으로 쓴다. 진행보드에 날짜 속성이 아직 없으면 이 규칙을 적용하기 전에 먼저 만든다.
- **"계획된 다음 스텝을 진행해줘" 같은 요청을 받으면, 사용자가 매번 짚어주지 않아도 스스로 진행보드부터 조회한다** — 지금 어떤 항목이 시작 전/진행 중/완료인지 먼저 확인하고, 그걸 근거로 다음에 뭘 해야 할지 판단한 뒤 착수와 동시에 그 항목을 "진행 중"으로 바꾼다. 이 확인 단계를 생략하고 곧장 작업부터 시작하면, 이미 완료된 항목을 다시 하거나 순서를 건너뛰는 실수로 이어질 수 있다.

## 6. 시각화를 적극 활용한다

사용자 본인이 흐름을 한눈에 파악하기 위해서, 그리고 다른 사람에게 프로젝트를 설명할 때도 쓸 수 있도록, 글로만 설명하지 않고 **머메이드(Mermaid) 다이어그램을 적극 활용**한다.

- 여러 단계·분기·순서가 있는 내용(실행 순서, 실험 플로우, 의사결정 기준, 데이터 파이프라인 등)은 표나 글머리 기호보다 **flowchart/sequence 다이어그램으로 먼저 그려보고**, 필요하면 글 설명을 보충한다.
- 성공지표 트리처럼 계층 구조가 있는 내용도 트리/그래프 다이어그램으로 표현한다.
- 일정이 걸리는 로드맵은 간트 차트(gantt)를 고려한다.
- 다이어그램은 "예쁘게 꾸미기용"이 아니라 **이해를 돕는 용도**이므로, 다이어그램 하나로 안 끝나면 옆에 짧은 설명을 같이 둔다.
- **여러 항목을 비교·나열하는 내용(설계 시점 추정치 vs 실측값, 여러 옵션 비교 등)은 표로 우선 정리한다** — 위 flowchart 우선 원칙은 흐름·분기·계층 구조에 해당하는 것이고, 값 여러 개를 나란히 비교하는 내용은 표가 더 명확하다. 이런 내용을 콜아웃(블록쿼트) 안에 밀도 높은 문단·불릿으로 욱여넣지 않는다 — 결국 사람이 읽어야 하는 문서이므로, 표·다이어그램으로 구조화된 형태가 문단보다 항상 우선이다.
- 노트북(.ipynb) 안에 넣는 개념 설명용 다이어그램은 `.claude/skills/notebook-toolkit`의 SVG/머메이드 컨벤션을 따른다. 이 절의 표·다이어그램 활용 원칙 자체는 Notion 반영본뿐 아니라 그 전 단계인 `docs/planning/`의 로컬 초안부터 적용한다 — 초안 단계에서 밀도 높은 문단으로 몰아 써두면 Notion 반영 시점에야 뒤늦게 표·다이어그램으로 바꾸는 이중 작업이 생긴다.
- **이 원칙은 신규 작성뿐 아니라 이미 써놓은 문서를 다시 훑을 때도 똑같이 적용한다 — "표로 만들라"는 요청을 받은 절만 고치고 문서의 나머지는 그대로 두지 않는다.** 문서 전체(모델카드·계획 문서 등)를 검토·버전업하는 작업을 맡으면, 요청받은 그 절뿐 아니라 문서 전반에 "여러 항목을 문장으로 죽 나열하는" 구간이 남아있는지 스스로 점검하고 같은 기준(표·다이어그램·명목화·계층 구조)으로 함께 정리한다 — 4-2절 명목화·6절 표 우선·4-4절 근거 절 표화 원칙이 문서의 어느 한 절에만 적용되고 나머지엔 예외로 남는 일이 없게 한다(2026-08-26 명시 — 근거 절만 표로 정리하라고 지시했는데 사용자가 "근거 위에도 정리 안 됐다, 그렇게 나열시키면 안 된다"고 문서 전체로 범위를 넓혀 재지적).

## 7. 프로젝트 시작 시 확인할 것

새 프로젝트를 시작하거나 기존 프로젝트 문서 작업을 요청받으면, 로컬에 새 마크다운 파일을 만들기 전에 **그 프로젝트의 관리용 Notion 페이지가 있는지부터 확인**한다. 있다면 그 안에서 작업하고, 없다면 사용자에게 만들지 물어본다. **`git-workflow.md` 1-1절에서 이미 이 프로젝트의 관리 툴·링크를 확인해 `CLAUDE.md`에 기록해뒀다면, 여기서 다시 사용자에게 묻지 않고 그 기록을 그대로 재사용한다** — 이 절의 "확인"은 아직 기록이 없을 때만 사용자에게 새로 묻는다는 뜻이다.

## 8. 하네스 기록용 페이지는 "참조 문서"처럼 간결하게

`.claude/agents`·`docs/harness` 구조를 정리해두는 Notion 페이지(4절의 프로젝트 기획 문서와는 성격이 다름 — 이건 "지금 하네스가 뭘로 구성돼 있는지"를 한눈에 훑어보는 카탈로그다)는 다음 기준을 따른다.

**이 페이지는 프로젝트마다 새로 만들지 않고 고정이다** — URL: https://app.notion.com/p/JY-Data-3c2ebec5c35780d59682e32cfb6b94d5 ("JY-Data"). 이 문서(`docs/harness/notion-workflow.md`) 자체가 하네스 포크 시 그대로 복사되는 대상이라(`git-workflow.md` 2절), 이 URL도 함께 이식되어 모든 프로젝트가 같은 하네스 기록 페이지를 공유한다 — 각 프로젝트의 4절 프로젝트 기획 페이지(프로젝트마다 다름, `CLAUDE.md`에 기록)와 혼동하지 않는다. **하네스의 기조가 바뀌면**(새 원칙 도입, 기존 원칙의 방향 전환 등 — 오타·서식 수정 같은 사소한 변경은 제외) 그 즉시 이 Notion 페이지도 함께 갱신한다.

**단, `git-workflow.md` 1절에서 "팀/회사 저장소"로 정했다면 이 URL을 그 저장소에 그대로 올리지 않는다** — 이 URL은 사용자 개인 Notion 계정 페이지라, 팀 저장소의 `docs/harness/`에 그대로 커밋되면 개인 계정 정보가 협업자에게 노출된다. 팀/회사 저장소로 하네스를 올리는 경우 이 문단(URL 포함)은 그 저장소용 사본에서 빼거나, 접근 권한이 이미 팀과 공유된 URL로 바꿔서 올린다.

- **메인 페이지 = 지금 상태를 훑어보는 카탈로그.** "무엇이 있다"(에이전트 목록, 스킬 목록, 파일 목록)를 표로, 한 항목당 한 줄 설명으로 압축한다. "왜 이렇게 됐는지"·"어떤 시행착오를 거쳤는지"·특정 세션의 사건 경위는 메인 페이지에 쓰지 않는다 — 궁금한 사람만 열어보도록 하위 페이지로 분리하고, 메인엔 링크 한 줄과 결론 한 줄만 남긴다.
- **표는 짧게.** 설명 칸은 되도록 한 문장 이내. 여러 줄짜리 설명이 필요하면 표에 욱여넣지 말고 하위 페이지로 뺀다.
- **다이어그램도 핵심 흐름만.** 범례·주석·색상 분류가 다이어그램 자체보다 커지면 과하다는 신호 — 꼭 필요한 노드/화살표만 남기고 나머지는 옆 텍스트나 하위 페이지로.
- **메인 페이지엔 날짜를 박지 않는다.** 이 페이지는 "지금 이 순간의 방향성·구조"를 계속 참고하는 카탈로그이지, 변경 이력을 남기는 로그가 아니다. `(2026-08-20 신설)` 같은 날짜 태그도 넣지 않는다 — "언제 바뀌었는지"는 git 커밋 이력이나 `HARNESS_LOG.md`가 이미 갖고 있으니 중복해서 남기지 않는다.
- 이 기준으로 다시 훑어봐도 좋을 신호: 메인 페이지의 어느 섹션이 스크롤 없이 한눈에 안 들어오면 그 섹션 내용의 상당수가 하위 페이지로 빠져야 할 후보다.
