# 통계 기반 관리자 대시보드 설계 가이드 (재사용 가능한 패턴)

`notion-workflow.md` 4절 5번은 "AB테스트/실험용 앱이라면 결과 확인용 백오피스 화면을 반드시 포함한다"까지만 정한다 — **그 백오피스가 통계 검정 결과(p-value, 신뢰구간, 가드레일 등)를 실시간에 가깝게 보여주는 경우**, 화면 하나만 달랑 만들면 통계를 잘 모르는 사용자에게는 숫자 나열로만 보이기 쉽다. 이 문서는 그런 상황에서 실제로 검증된 설계 패턴을 모아둔다. 백오피스가 단순 CRUD·조회용이라면 이 문서는 해당하지 않는다.

> **이 문서를 읽는 법 — 색상표·px 값이 아니라 판단 기준을 가져간다.** 10절 이후는 실제 시안(Artifact)을 놓고 100회 안팎의 시각 피드백을 주고받으며 걸러진 QA 원칙이다. 거기 나오는 구체적 hex 색상·px 수치·"보라 알약형 토글" 같은 특정 형태는 **이 프로젝트 이 화면 하나에 한정된 결과물**이지 재사용 대상이 아니다(`CLAUDE.md` 행동 지침 — "관리자용 백오피스의 디자인 스타일은 참여자용 실제 프론트엔드에 절대 그대로 반영하지 않는다"와 같은 이유로, 다음 백오피스에도 이 색·이 모양을 그대로 베끼면 안 된다). 다음에 새 백오피스를 만들 때 가져가야 할 것은 **"왜 그렇게 고쳤는지"의 판단 기준**뿐이다 — 매번 그 프로젝트의 톤앤매너·데이터 성격에 맞는 새 색상·레이아웃을 다시 정하되, 아래 체크(대비를 검증했는가, 위계가 다른 토글을 구분했는가 등)는 빠짐없이 스스로 통과시킨다.

## 1. "목표 흐름 패널"을 대시보드 상단에 둔다

**대시보드는 숫자만 보여주고 끝나면 안 된다 — 그 숫자가 성공지표 트리의 어느 단계에 해당하는지를 항상 다시 확인할 수 있어야 한다.** North Star → 핵심 가설 → 가드레일(사전 검증) → 1차 지표(판단 기준) → 보조 지표로 이어지는 흐름을, 접이식 패널로 대시보드 최상단에 둔다(항상 펼쳐두면 화면을 차지하니 기본은 접힌 상태, 클릭 한 번으로 언제든 다시 볼 수 있게).

- 이 패널의 내용은 그 프로젝트의 "성공지표 트리" 문서(`notion-workflow.md` 4절의 문서 체계라면 04번)를 그대로 요약한 것이다 — 새로 설계하지 않고 이미 확정된 트리를 옮겨온다.
- 참여자 응답이 쌓이는 동안 사용자가 "지금 이게 뭘 확인하는 중인지" 헷갈리지 않게 하는 게 목적이다 — 수치 하나하나를 따로 보면 맥락을 잊기 쉽다.

## 2. 판정은 배지로 — 단, "유의미하지 않음"을 "나쁨"으로 표시하지 않는다

**모든 통계 결과 카드에 좋음/보류 상태를 한눈에 보여주는 배지를 붙인다** — 숫자만 던지면 통계에 익숙하지 않은 사용자는 좋은 값인지 나쁜 값인지 스스로 판단해야 한다.

- **가드레일(순서효과, SRM 등)**: 통과(✅ 정상) / 실패(⚠️ 이상) 이분법이 맞다 — 가드레일은 실제로 "통과해야만 아래 결과를 신뢰할 수 있는" 게이트이기 때문이다.
- **1차·보조 지표(유의성 검정)**: 이분법을 쓰지 않는다. `p < 0.05`(또는 프로젝트가 정한 임계값)를 넘기면 "✅ 유의미해요", 못 넘기면 절대 "❌ 나쁨"이 아니라 "🔍 아직 판단하기 일러요 — 표본이 더 필요할 수 있어요"로 표현한다. 통계적으로 "유의미하지 않음"은 "차이가 없다"는 증거가 아니라 "이 표본 크기로는 못 잡아냈다"는 뜻일 뿐이다 — 이 구분을 배지 문구 단계에서부터 지킨다(성공지표 트리 문서가 이미 이 원칙을 명시하고 있다면 그 문구를 그대로 재사용한다).
- 색상은 의미론적으로 고정한다 — 초록=정상/유의미, 회색 또는 중립색=보류, 주황/노랑=주의가 필요한 가드레일 실패. 빨강은 되도록 아끼고(가드레일 실패처럼 정말 "결과를 못 믿는" 상황에만), 단순히 "아직 유의미하지 않음"에는 쓰지 않는다.

## 3. 용어 설명은 툴팁이 아니라 섹션 아래 접이식(아코디언)으로 둔다

**툴팁(마우스 호버 기반)은 터치 기기에서 애초에 작동하지 않는다** — 관리자가 모바일로 확인할 가능성이 있다면(반응형 대시보드라면 당연히 있다) 툴팁은 후보에서 제외한다. 대신 각 지표 카드 하단에 "❓ 이 결과, 무슨 뜻이에요?" 버튼을 두고, 클릭하면 펼쳐지는 설명 패널을 쓴다 — 클릭(터치) 기반이라 모든 기기에서 동일하게 동작한다.

설명은 항상 3단 구조를 쓴다:
1. **이게 뭔가요** — 용어 자체의 정의(전문 용어 없이 풀어서)
2. **왜 확인하나요 / 왜 중요한가요** — 이 지표가 결과 해석에서 하는 역할
3. **어떻게 읽나요** — 실제 화면의 숫자를 어떻게 해석해야 하는지(임계값 기준 포함)

## 4. 시간축에는 유의성 지표를 올리지 않는다 — 원시 카운트만 시계열로

**"p값·신뢰구간이 시간에 따라 어떻게 변해왔는지" 그래프는 절대 만들지 않는다.** 이런 그래프는 관리자가 "지금 유의미해지려는 참인가"를 실시간으로 지켜보게 만들어, No peeking(조기 종료·추가 모집 금지) 사전 등록 원칙을 스스로 어기고 싶은 유혹을 구조적으로 키운다 — 대시보드 편의성 자체가 리스크가 되는 지점이다(`ml-project-workflow.md`·실험 설계 문서의 사전 등록 원칙과 직접 충돌).

- **안전한 시계열**: 누적 응답 수(표본이 얼마나 모였는지)처럼, 판단에 영향을 주지 않는 순수 진행 상황 지표만 시간 추이로 보여준다.
- **위험한 시계열**: p-value, 신뢰구간, 승자 여부 등 "판단 기준" 자체가 시간에 따라 어떻게 움직였는지 — 이런 건 화면에 아예 넣지 않는다.
- 이 대시보드를 설계하는 프로젝트의 리스크 체크리스트에 "관리자 자신의 self-peeking" 위험이 이미 있다면(백오피스 신설 시 표준으로 점검해야 하는 항목, 9절 참고) 이 절이 그 위험의 구체적 완화 방법 중 하나다.

## 5. 시각화는 통계 목적에 맞춰 고른다 — 막대바 하나로 다 때우지 않는다

| 목적 | 적합한 시각화 |
|---|---|
| 두 값(A vs B) 비교 | 가로 막대 비교 |
| 유의성 검정 + 신뢰구간 | 0~100% 축 + 신뢰구간 밴드 + 기준선(예: 무선호 50%) — 밴드가 기준선을 벗어나는지 한눈에 보이게 |
| 짝지어진 이진 데이터(McNemar 등) | 2×2 사분면 그리드 — 실제 검정이 보는 대각선 두 칸을 시각적으로 대응시킨다 |
| 구성비(품목별 응답 분포 등) | 도넛/파이 |
| 그룹 쏠림(SRM) | 중앙 기준선이 있는 분할 막대(균등 배정이면 정확히 반으로 갈리는 형태) |
| 진행 상황(누적 표본수) | 스파크라인(4절 원칙 준수 — 판단 지표는 올리지 않음) |
| 여러 축으로 교차 대조(순서별×품목별 등) | "요약" 탭과 분리된 "세부 비교" 탭에서 그룹 막대 + 토글로 전환 |

같은 막대바 컴포넌트를 모든 지표에 재사용하면 "다양한 통계를 다각도로 본다"는 대시보드의 존재 이유가 흐려진다 — 각 통계 개념이 실제로 무엇을 비교하는지가 시각화 형태에 그대로 드러나야 한다.

## 6. 요약과 세부 비교를 분리하되, 탭의 범위는 실제로 "대안 뷰"가 있는 영역에만 국한한다

핵심 지표와 교차 대조(순서별·품목별 등 여러 축으로 같은 데이터를 쪼개보는 뷰)는 분리해서 보여준다 — 하나의 화면에 다 몰아넣으면 스크롤이 길어지고, 처음 보는 사람은 뭐가 핵심이고 뭐가 부가 정보인지 구분하기 어렵다.

**단, 이 분리를 "페이지 전체를 두 탭으로 통째로 스왑"하는 식으로 구현하면 안 된다.** 교차 대조용 "대안 뷰"가 실제로 존재하는 지표(예: 1차 지표의 "핵심 요약 ↔ 순서별·품목별 대조")만 그 지표 카드 안에 로컬 토글로 넣고, 대안 뷰가 없는 지표(가드레일, 보조 지표 요약, 품목별 분포 등)는 탭과 무관하게 항상 그 자리에 그대로 보여준다. 탭/토글을 설계하기 전에 먼저 "이 콘텐츠에 정말 서로 다른 두 가지 뷰가 있는가, 아니면 그냥 순서상 아래에 있을 뿐인가"를 항목별로 점검한다 — 후자를 탭 안에 가두면 항상 봐야 할 정보가 특정 탭에서만 사라지는 사고가 난다.

## 7. 반응형 — 나란히 배치는 좁은 화면에서 항상 세로로 쌓는다

가드레일 카드 2개를 나란히, A/B 인원을 나란히 배치하는 식의 레이아웃은 데스크톱 폭에서는 괜찮지만 모바일 폭(약 375~390px)에서는 그대로 두면 글자가 찌그러진다. 그리드 기반 레이아웃을 쓰고, 좁은 화면에서는 명시적으로 1열로 강제 전환한다. 표(테이블)로 조밀한 데이터를 보여줘야 한다면 가로 스크롤 컨테이너로 감싸 페이지 자체는 가로로 안 밀리게 한다.

## 8. 계산 로직은 새로 만들지 않는다

이 대시보드가 보여주는 통계(이항검정, Wilson CI, McNemar, 가드레일 등)는 이미 프로젝트의 분석 단계(예: `ml-project-workflow.md` 11절의 모델링·평가 계획서, 또는 AB테스트라면 실험설계서)에서 정의된 순수 함수를 재사용해야 한다 — 결과 보고서용 최종 분석과 대시보드가 서로 다른 계산식을 쓰면 두 수치가 어긋나는 사고가 생긴다.

## 9. 접근 제어는 규모에 맞춘다

파일럿·소규모 프로젝트(관리자 1인)라면 최소 비밀번호 게이트로 충분하다 — 역할별 권한 관리 같은 프로덕션 수준 인증을 미리 만들지 않는다(`karpathy_skills.md` 2️⃣ Simplicity First와 같은 원칙). 다만 참여자 응답 데이터가 노출되는 화면이라는 점은 리스크 체크리스트에 별도 항목으로 남긴다(자세한 위험 분류는 위 4절의 self-peeking 위험과 함께 다룬다).

## 10. 활성/비활성 상태는 배경과 글자 둘 다 대비를 확인한다

토글·탭·칩 같은 인터랙션 요소는 "활성 상태가 비활성 상태보다 안 보이는" 역전 사고가 특히 잦다 — 서로 다른 컴포넌트(탭, 전환 버튼, 칩)에서 반복적으로 재발하는 흔한 패턴이다. 원인은 항상 같다: 다크 모드용으로 골라둔 밝은 시맨틱 색(예: `--accent`의 라벤더)을 흰 글자와 함께 그대로 "칠해진 배경"으로 재사용한 것 — 옅은 배경 위 짙은 글자에는 어울리던 색이, 흰 글자를 얹는 진한 배경으로 쓰이는 순간 대비가 반대로 무너진다.

- 배경으로 칠할 색과 글자색으로 쓸 색은 **같은 토큰을 재사용하지 않는다.** "칠해진 배경 위 흰 글자"용으로는 라이트/다크 상관없이 항상 충분히 어두운 값을 쓰는 별도 토큰(이 프로젝트의 `-solid` 계열처럼 테마 불변으로 고정한 값)을 만들고, "옅은 배경 위 글자색"용 토큰과 절대 겸용하지 않는다.
- 활성 상태를 만들 때마다 "지금 이 배경에 이 글자색이 실제로 잘 읽히는가"를 값으로만 판단하지 말고 렌더링해서 눈으로 확인한다 — 토큰 이름이 맞아 보여도(`--accent`니까 강조색이겠지) 용도가 안 맞으면 대비가 깨진다.

## 11. `filter`는 배경까지 물들인다 — 텍스트만 보정하려면 별도 요소로 감싼다

`filter: saturate()`나 `color-mix()`로 글자만 더 선명하게/밝게 만들려다가, 같은 요소의 배경색까지 같이 물드는 실수가 반복됐다(토글 활성 버튼의 배경이 원했던 순수 배경색이 아니라 옅게 채도가 낀 색으로 보였던 사고). `filter`는 해당 요소가 렌더링하는 모든 픽셀(배경 포함)에 적용되는 합성 효과라서, 글자에만 걸고 싶으면 **글자를 별도의 자식 `<span>`으로 감싸고 그 span에만 `filter`/`color-mix`를 건다** — 부모 요소(배경을 칠하는 쪽)는 건드리지 않는다.

## 12. 아이콘·짧은 라벨의 수직 중앙 정렬은 padding 비대칭보다 flex 고정 높이가 안전하다

칩·배지 안 텍스트가 "위로 살짝 쏠려 보이는" 문제를 padding-top/bottom을 비대칭으로 조정하거나 `position: relative; top: 1px` 같은 미세 보정으로 고치려 하면, 폰트(특히 한글 혼용 폰트)의 실제 글리프 높이가 브라우저·폰트마다 달라서 몇 번을 조정해도 다시 안 맞는 경우가 많았다. 확실한 방법은 **`display:flex; align-items:center;`에 고정 `height`를 준 컨테이너**를 쓰는 것이다 — 내용물(아이콘이든 텍스트든)이 그 안에서 항상 기하학적으로 정중앙에 오므로 폰트 메트릭에 좌우되지 않는다. 아이콘+텍스트 조합(예: "✓ 정상")도 같은 원칙 — 아이콘을 감싸는 원형 배지를 flex로 만들면 아이콘과 텍스트 각각의 기준선이 달라도 흔들리지 않는다.

## 13. SVG 차트: `preserveAspectRatio="none"`은 원형 마커를 찌그러뜨린다

라인/영역 차트의 viewBox 가로세로 비율과 실제 렌더링 폭이 다를 때 `preserveAspectRatio="none"`으로 강제로 채우면, 그 차트의 좌표계 안에 있는 모든 도형이 x/y 비율이 다르게 스케일된다 — 사각형·선은 티가 안 나지만 **`<circle>`처럼 rx=ry인 도형은 타원으로 찌그러진다.** 끝점을 강조하는 원형 마커가 필요하면 SVG 내부에 그리지 말고, 부모를 `position: relative`로 두고 **고정 픽셀 크기의 CSS `div`(border-radius:50%)를 퍼센트 좌표로 오버레이**한다 — CSS로 그린 도형은 SVG 내부 좌표계의 비균등 스케일과 무관하게 항상 정원을 유지한다.

## 14. "이 값들만 비교 대상" 같은 부분집합 관계는 색상 하나로 표현하지 않는다

McNemar 2×2 그리드처럼 한 화면에 있는 항목 중 일부만 실제 통계 계산에 쓰이는 경우("이 대각선 두 칸만 비교해요"), 색상 구분만으로는 안 보인다는 지적을 받았다("이건 대각선이 없는데? 뭘 보라는거지?"). **최소 두 가지 중복 신호를 함께 쓴다**: ① 비교 대상 칸에는 점선 테두리 같은 명확한 시각적 경계, ② "비교 대상" 같은 짧은 라벨 배지. 대신 비교 대상이 아닌 칸은 (완전히 숨기지 않고) 살짝 옅게 눌러서 상대적으로 덜 중요하다는 걸 보여준다 — 지워버리면 전체 맥락(예: 전체 응답 수)을 잃는다.

## 15. 숫자에는 예외 없이 단위를 붙인다

"11/24", "24 vs 23"처럼 맥락상 명확해 보이는 숫자쌍도 실제로는 "이게 명 수야 비율이야?" 하는 질문을 반복적으로 받았다. 사람 수를 나타내는 모든 숫자에 "명"을 붙이고, 그 숫자가 정확히 무엇을 세고 있는지(예: "A→B: B안 선호 11/24명")까지 짧게라도 라벨링한다 — 화면 공간이 빠듯해서 줄이고 싶어도 단위만은 마지막까지 남긴다.

## 16. 중첩된 토글은 깊이(depth)마다 다른 시각 언어를 쓴다

한 카드 안에 "뷰 전환"(예: 핵심 요약 ↔ 순서별·품목별 대조)과 그 안의 "축 전환"(예: 순서별 ↔ 품목별)처럼 서로 다른 층위의 토글이 중첩되면, 똑같은 모양(같은 알약형 버튼)을 쓸 경우 사용자가 "어느 버튼이 뭘 바꾸는지" 헷갈린다. 상위(페이지/카드 단위 모드 전환)는 눈에 띄는 알약형 세그먼트 버튼으로, 하위(그 안에서의 축 전환)는 밑줄형 탭처럼 더 조용한 형태로 — 깊이가 다르면 형태도 다르게 만들어 위계를 시각적으로 드러낸다.

## 17. 여백이 안 늘어나는 버그는 원인이 다양하다 — padding vs margin, inline style, 컴포넌트 중첩

"여백을 넓혀달라"는 요청에 CSS 값을 계속 키워도 반영이 안 되거나 엉뚱한 곳이 커지는 사고가 여러 번 있었다. 흔한 원인 세 가지:

- **컴포넌트 자체의 padding을 키우는 것과, 그 컴포넌트와 이웃 요소 사이의 margin을 넓히는 것은 다른 문제다.** "탭버튼과 콘텐츠 사이를 띄워달라"는 요청에 탭버튼의 padding을 키우면 버튼 자체가 커질 뿐 간격은 그대로다 — 이웃 사이 여백은 `margin`으로, 요소 내부 여백은 `padding`으로 명확히 구분해서 고친다.
- **인라인 `style="padding:16px"` 같은 하드코딩은 이후의 모든 CSS 클래스 기반 여백 조정을 무력화한다.** 나중에 클래스에서 padding을 아무리 늘려도 인라인 스타일이 우선 적용돼 반영되지 않는다 — 반복적으로 "안 늘어난다"는 지적을 받으면 인라인 style부터 의심한다.
- **카드 하단에 딱 붙어야 하는 아코디언 트리거(예: "이 결과, 무슨 뜻이에요?" 버튼)를 콘텐츠와 같은 padding 컨테이너 안에 넣으면 카드 가장자리에 붙지 못한다.** 이런 컴포넌트는 콘텐츠를 감싸는 padding 래퍼의 **바깥**, 카드(`overflow:hidden` + 둥근 모서리)의 직접 자식으로 둬야 카드 하단 모서리에 자연스럽게 잘려 붙는다.

## 근거

이 문서는 실제 프로젝트 세션에서 사용자가 순서대로 요청한 것들을 반영해 만들어졌다 — 반응형(모바일 대응) 여부 확인, 통계 용어를 모르는 사람도 이해할 수 있게 툴팁·섹션 설명 요구, "좋은 값/나쁜 값"을 한눈에 판단할 수 있는 표시 요구, 결과 자료를 다각도로 대조·시각화해야 한다는 지적, 분석 방향 자체가 불명확하다는 지적과 수집 도중 실시간 확인 요구가 순서대로 있었다. 각 요청에 대응해 실제로 시안(Artifact)을 만들며 검증한 패턴만 이 문서에 남겼다 — 검증 안 된 아이디어는 넣지 않았다.

**10~17절은 같은 시안을 두고 이어진 후속 세션에서, 100회 안팎의 스크린샷 기반 시각 피드백 중 실제로 2회 이상 반복 발생한 버그 패턴만 추려 일반화해 추가했다.** 한 번만 발생한 개별 취향(정확한 hex 값, 여백 몇 px 등)은 이 문서에 옮기지 않았다 — 그런 값은 다음 백오피스에서 새로 정해야 할 대상이기 때문이다(문서 상단 안내 상자 참고). 사용자가 다음 백오피스 작업에서도 톤앤매너·레이아웃이 판박이로 반복되지 않도록 이번에 잡아낸 시각 QA 판단 기준을 하네스 문서로 일반화해달라고 명시적으로 요청해 신설했다.
