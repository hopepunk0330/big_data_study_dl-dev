# 깃허브 관리 방식 (재사용 가능한 패턴)

새 데이터 프로젝트를 시작할 때 참고하는 git/GitHub 운영 체크리스트. PR 승인 담당자 재확인, PR 문구 규칙, push 전 허락 규칙은 `CLAUDE.md` 금지·행동지침 항목에 이미 있으므로 여기서는 반복하지 않는다.

## 1. 저장소를 나눌지 먼저 정한다

학습/작업 성격에 따라 저장소가 하나가 아니라 여러 개일 수 있다 (예: 개인 학습 기록용 저장소 + 팀/회사 제출용 저장소). 새 프로젝트를 시작할 때 다음을 사용자에게 먼저 확인한다:

- 개인용 저장소가 따로 필요한가, 아니면 팀/회사 저장소 하나로 충분한가?
- 개인용이라면 거기에 하네스(`.claude/`, `docs/harness/`)까지 같이 올릴지, 작업물만 올릴지?
- 팀/회사용이라면 본인 담당 범위만 올리는지, 전체를 공유하는지?

### 1-1. 프로젝트 보고·관리 툴과 링크를 확인한다

**하네스 자체를 기록하는 Notion 페이지(`notion-workflow.md` 8절, "JY-Data")는 모든 프로젝트가 공유하는 고정 페이지라 새로 물어볼 필요가 없다.** 하지만 **이 프로젝트의 진행상황·기획 문서를 관리하는 툴**은 프로젝트마다 다를 수 있다 — Notion일 수도, Slack일 수도, 다른 MCP 연결 도구일 수도 있다. 새 프로젝트를 시작할 때(또는 아래 8절 절차로 하네스를 포크해올 때) 사용자에게 다음을 확인한다:

- 이 프로젝트의 진행상황을 어느 툴로 관리할 것인가(Notion/Slack/기타)?
- 그 툴의 프로젝트 페이지·채널 링크는 무엇인가?

확인한 답은 그 프로젝트의 `CLAUDE.md` 개요에 링크와 함께 기록한다(이 프로젝트 `CLAUDE.md`의 "Notion 프로젝트 페이지" 문장이 예시다) — 이후 `docs/planning/` 문서 작업 시 이 링크로 자동 동기화하고, 매 세션 다시 링크를 찾거나 사용자에게 되묻지 않는다.

**프로젝트를 리셋할 때(`CLAUDE.md` 리셋·프로젝트 구조 초기화)도 이 확인 절차를 다시 거친다** — 리셋은 프로젝트 성격이 바뀌었을 가능성을 전제하므로, 이전 링크를 그대로 들고 가지 않고 사용자에게 다시 확인한다.

### 1-2. 배포 URL도 확인 즉시 CLAUDE.md에 기록한다

**Vercel·Streamlit Community Cloud 등에 실제로 배포한 뒤 그 URL을 알게 되는 순간, 관리 툴 링크(1-1절)와 똑같은 방식으로 그 프로젝트의 `CLAUDE.md` 개요에 즉시 적어둔다** — 다음 세션이나 몇 턴 뒤에 그 URL이 다시 필요해질 때 사용자에게 되묻지 않기 위해서다. 배포를 실행한 그 세션이 URL을 알아냈다면(빌드 로그, 배포 완료 메시지 등) 그 턴 안에 바로 기록한다. 사용자가 먼저 URL을 알려준 경우(직접 찾아서 공유해준 경우)도 마찬가지로 즉시 기록한다 — "필요할 때 다시 물어보면 되지"라고 미루지 않는다.

**근거**: 이 프로젝트에서 백오피스(Streamlit)를 배포해놓고도 CLAUDE.md 어디에도 그 URL을 남기지 않아, 나중에 배포 상태를 확인하려 할 때 사용자가 직접 URL을 다시 찾아 알려주며 왜 저장해두지 않았느냐고 지적한 것을 계기로 신설했다(2026-08-27) — 이 사건은 `karpathy_skills.md`의 "반복되는 문제는 발견 즉시 하네스에 반영한다" 실천 규칙의 실제 적용 사례이기도 하다.

### 1-3. 새로 배포할 때는 그 배포 서비스의 방식을 옵션으로 비교해서 사용자가 고르게 한다(2026-08-28 신설)

**새 프로젝트를 처음 배포하거나 배포 설정(정적 파일 위치, 라우팅/설정 파일 작성 여부 등)을 정할 때, 관습적인 값을 임의로 골라 진행하지 않는다.** 그 배포 서비스(Vercel·Netlify·Firebase Hosting·GitHub Pages 등)가 실제로 어떻게 동작하는지, 다른 서비스와 무엇이 다른지를 표나 비교 목록으로 먼저 설명하고, 선택지 각각의 장단점(언제 필요한지·유지보수 부담 등)을 곁들여 사용자가 직접 고르게 한다 — Claude가 "이게 정답"이라고 단정하지 않는다. 추천 의견을 낼 수는 있지만, 그 추천을 승인 없이 그대로 실행에 옮기지 않는다(이 문서 전반의 push 승인 원칙, `CLAUDE.md` "새로운 작업 방향 승인" 원칙과 같은 정신).

**근거**: 이 프로젝트에서 Vercel 배포 폴더 구조(정적 파일을 `public/` 서브폴더에 둘지 프로젝트 루트에 둘지)와 `vercel.json` 작성 여부를 논의하며, `public/` 폴더 관습이 Vercel 전용인지 다른 배포 서비스와 어떻게 다른지 사용자가 직접 물어봤다. 그 답으로 여러 서비스(Vercel/Netlify/Firebase Hosting/GitHub Pages)의 정적 파일 위치 관습을 비교해 설명하자 사용자가 이 방식을 마음에 들어했고, 앞으로 다른 프로젝트에서도 배포 설정을 정할 때는 항상 이렇게 그 배포 서비스의 방식을 옵션으로 설명하고 사용자가 선택하게 하라고 명시적으로 요청해(2026-08-28) 이 절을 신설했다.

## 2. 이식 가능 범위는 정해져 있다

- **하네스 브랜치 분리도 이식 항목이다(2026-08-20 신설)**: 새 프로젝트에서도 처음부터 8절의 `harness` 브랜치 + `{프로젝트폴더명}-harness-work` worktree 패턴을 적용한다 — 나중에 프로젝트가 커진 뒤에 뒤늦게 분리하려 하면 이미 `main`에 하네스 이력이 섞여 들어가 `filter-repo`로 과거 이력까지 정리해야 하는 번거로움이 생긴다(8절 "완성본을 공유할 때" 참고). 처음부터 분리해두면 이 수고를 피할 수 있다.

- **이식 대상(그대로 재사용)**: `.claude/agents/`, `.claude/skills/`, `docs/harness/` — 고칠 필요 없이 그대로 복사해서 쓴다. **단 하나의 예외**: `notion-workflow.md` 8절의 "JY-Data" 고정 URL 문단은 개인용 저장소일 때만 그대로 두고, 팀/회사 저장소(위 1절에서 그렇게 정했다면)로 이식할 땐 그 문단만 8절 자신이 명시한 대로 빼거나 팀 공유 URL로 바꾼다 — 개인 Notion 계정이 협업자에게 노출되는 걸 막기 위한 유일한 조건부 수정이다.
- **이식 대상(복사 후 프로젝트에 맞게 수정) — `CLAUDE.md`(2026-08-20, 사용자 지적으로 "이식 대상 아님"에서 정정)**: `CLAUDE.md`도 이 하네스의 일부이므로 **포크할 때 절대 빠뜨리지 않는다.** 다만 위 세 항목과 달리 그대로 재사용하는 게 아니라 **초안(템플릿)으로 복사한 뒤 그 프로젝트에 맞는 부분만 수정**한다 — 코딩 규칙·검증 명령·금지 항목·행동 지침처럼 프로젝트마다 값이 달라지는 내용이 섞여 있기 때문이다. 절차:
  1. 이전 프로젝트의 `CLAUDE.md`를 새 프로젝트로 그대로 복사해온다.
  2. **반드시 새 프로젝트의 세션에서** "이 프로젝트에 안 맞는 내용은 지우고, 안 정해진 부분은 새로 확인해서 채운다" — 이전 프로젝트 세션에서 새 프로젝트의 컨벤션을 미리 정해버리면 두 프로젝트 맥락이 섞이므로, 이전 세션이 할 수 있는 건 파일을 그대로 복사해두는 것까지다.
  섹션 구조(개요/코딩 규칙/검증 명령/금지/행동 지침) 자체를 매번 처음부터 고민하지 않아도 되는 게 장점이다.
- **이식 대상(내용은 비우고 스캐폴드만 재사용) — `.claude/agent-memory/`**: 이 폴더는 위 세 항목(그대로 재사용)과도, 아래 "이식 대상 아님" 항목들과도 다른 세 번째 범주다. **내용**(그 프로젝트에서 실제로 다룬 파일명·수치·세션 이력)은 절대 가져가지 않지만, **빈 템플릿(스캐폴드) 자체는 하네스의 일부로 이식한다** — 상세 절차(포크 시 Claude가 각 에이전트 폴더에 빈 `index.md`/`recent.md`를 직접 새로 만드는 것)는 `memory-protocol.md`의 "하네스를 새 프로젝트로 포크할 때" 절을 따른다. **`CLAUDE.md`의 "복사 후 수정" 절차와 헷갈리지 않는다** — `CLAUDE.md`는 파일을 그대로 복사해온 뒤 내용을 수정하고, `agent-memory/`는 파일을 복사하지 않고 매번 새로 빈 템플릿을 만든다. 결과물이 비슷해 보여도(둘 다 "그대로 재사용은 안 됨") 만드는 방식이 다르다.
- **이식 대상 아님**: 그 프로젝트의 실제 작업물 폴더(예: `과제/`, `data/`), 프로젝트 전용 스크립트/대본(예: `docs/review-scripts/`), **PM 기획 문서 초안(`docs/planning/`, 버전별로 `old/`에 보존 — `notion-workflow.md` 4-1절 참고)**.

## 3. 커밋/PR 컨벤션은 매번 다시 묻는다

커밋 메시지 형식, PR 본문에 넣을 고정 문구(예: 특정 프로젝트에서 "과제 제출"/"과제 올렸으니 확인해 주세요" 같은 것) 는 프로젝트나 팀마다 다르다. 이전 프로젝트에서 쓰던 문구를 새 프로젝트에 그대로 재사용하지 않고, 매번 확인해서 정한다.

### 3-1. 로컬 커밋은 매번 허락받지 않는다 — push만 허락받는다(2026-08-21 명시)

**의미 있는 작업 단위가 끝나면(문서 한 편 완성, 하네스 수정 라운드 종료 등) 그때마다 물어보지 않고 바로 로컬 커밋한다.** `git commit`은 그 브랜치 안에서 되돌릴 수 있는 로컬 작업이라, 잘못됐을 때 `git revert`·`git reset`으로 언제든 복구 가능하다는 게 이유다 — 반면 원격 저장소로 `push`하는 것은 다른 사람·다른 기기와 상태를 공유하는 행위라 되돌리기가 더 무겁고(강제 push 필요), `CLAUDE.md` 금지 항목대로 여전히 **매번 명시적 허락**을 받는다.

- 커밋 메시지 컨벤션(3절)은 그대로 지키되, "커밋해도 되냐"는 확인 자체는 생략한다.
- 무엇을 커밋하는지는 항상 투명하게 보고한다(무슨 파일을, 왜) — 허락을 안 구하는 것이지 보고를 생략하는 게 아니다.
- 커밋 범위는 논리적 단위로 나눈다(관련 없는 변경을 한 커밋에 몰아넣지 않음) — 되돌릴 때 필요한 것만 되돌릴 수 있어야 로컬 커밋의 "안전망" 역할이 실제로 작동한다.
- `git add -A`/`git add .`처럼 통째로 스테이징하지 않고, 커밋할 파일을 항상 이름으로 지정한다 — 시스템 지침의 "Git Safety Protocol"(민감 파일 실수 포함 방지)은 이 자동 커밋 관행에서도 그대로 적용된다.
- 이 규칙은 **일반 커밋에만** 적용된다. `--amend`, `push --force`, `reset --hard` 같은 이력을 재작성하거나 파괴적인 명령은 여전히 원칙대로 사용자 명시적 요청이 있을 때만 쓴다(시스템 지침 Git Safety Protocol 그대로 유지).

### 3-2. 로컬 커밋을 쌓아만 두지 않는다 — 시점이 되면 push를 먼저 제안한다(2026-08-21 명시)

**"push는 허락받는다"가 "사용자가 먼저 물어볼 때까지 조용히 쌓아둔다"는 뜻이 아니다.** 3-1은 push의 실행 여부·타이밍을 사용자가 결정한다는 뜻이지, 그 결정 자체를 사용자가 먼저 꺼내야 한다는 뜻이 아니다 — 자연스러운 체크포인트가 오면 먼저 "지금까지 로컬에 N개 커밋 쌓였는데 push할까요?"라고 제안한다. 체크포인트 예시:
- PM 로드맵의 한 단계(원페이저·PRD 등 문서 하나)가 완결됐을 때
- 하네스 수정 라운드가 끝나 `data-harness-auditor`를 돌린 직후
- ML 노트북 한 편(예: EDA·전처리 등 파이프라인 초반 단계 하나)이 끝까지 돌아가고 결과가 확정됐을 때
- 위 계기가 한동안 없더라도, origin 대비 쌓인 미푸시 커밋이 대략 5개를 넘어가면 그 자체를 계기로 제안한다
- 세션을 마무리하는 시점(사용자가 대화를 끝내려는 낌새)에도 미푸시 커밋이 있으면 짚고 넘어간다

제안만 하고 실행은 사용자 답을 받은 뒤에 한다(3-1의 push 허락 규칙은 그대로 유지) — 이 절이 바꾸는 건 "먼저 말을 꺼내느냐"이지 "허락 없이 push하느냐"가 아니다.

## 5. 원격 연결을 정리할 때

- **로컬 정리**: 더는 안 쓰는 원격 저장소는 `git remote remove <이름>`으로 로컬 연결을 끊거나, 별도 로컬 클론 폴더였다면 그 폴더를 지우면 된다. 삭제 전엔 항상 `git status`로 커밋 안 된 변경사항이 없는지 확인한다.
- **GitHub 쪽 정리는 별개**: 저장소 나가기, 협업자 권한 회수, 저장소 자체 삭제 같은 건 git 명령이 아니라 GitHub 웹/설정에서 직접 하는 작업이다. "연결을 끊는다"고 할 때 로컬 정리를 말하는 건지 GitHub 접근 권한 정리를 말하는 건지 매번 구분해서 확인한다.

## 6. 하네스가 여러 프로젝트로 포크됐을 때 최신 버전 추적

하네스는 git submodule이 아니라 단순 파일 복사(`cp -r .claude/ docs/harness/`)로 프로젝트 간에 옮겨진다. 그래서 A 프로젝트에서 포크한 하네스를 B에서 더 발전시키고, B에서 다시 C로 포크하는 식으로 여러 갈래로 나뉠 수 있다 — 이때 "어느 사본이 최신인지"를 다음 두 가지로 판단한다.

**`cp -r`은 `.gitignore`를 안 본다** — `node_modules/`처럼 무겁고 플랫폼 종속적인 폴더(예: `docs/harness/report-tools/`)가 있으면 그대로 복사돼버린다. 포크할 때는 그런 폴더를 제외하고 복사한 뒤(`rsync -a --exclude=node_modules/ ...` 등), 새 프로젝트에서 해당 폴더의 `package.json` 기준으로 `npm install`을 새로 돌린다.

**`docs/harness/report-tools/`는 범용 도구(`svg_to_png.mjs`·`html_to_pdf.mjs` 등)와 그 프로젝트 전용 검증 스크립트(특정 화면·특정 버그 라운드의 DOM 구조에 강결합된 것)가 섞이기 쉽다 — 포크할 때 이 둘을 구분한다.** 범용 도구는 포크 대상 그대로 가져가고, 특정 프로젝트의 화면 셀렉터·버그 라운드에 강결합된 스크립트(예: 이 프로젝트의 `verify_scr004_modal_pan.mjs`처럼 `.p3-sheet`·`#pv4-confirm` 같은 이 프로젝트 고유 DOM에 의존하는 것)는 새 프로젝트에서 재사용 불가능하므로 포크 시 제외한다 — 애매하면 스크립트 상단 주석에 "이 프로젝트 전용" 표시가 있는지 확인한다(`_flow_helpers.mjs` 같은 프로젝트 전용 공용 헬퍼도 같은 이유로 제외 대상). 이 폴더에 쌓인 스크립트가 늘어날수록 범용/전용 구분이 흐려지므로, 하네스를 고칠 때마다(git-workflow.md 7절) 이 폴더도 함께 훑어 더는 안 쓰는 프로젝트 전용 스크립트·스크린샷은 정리(prune)하는 걸 권장한다 — 다만 이 정리는 판단이 필요한 작업이라 자동 실행 대상은 아니다.

- **1순위: git 커밋 기록** — 하네스를 고칠 때마다 그 프로젝트 저장소에 커밋해서 남긴다(새 파일 만들고 끝내지 않는다). 여러 프로젝트 중 최신을 고를 땐 각 저장소에서 아래 명령으로 마지막 변경 날짜를 비교한다:
  ```
  git log -1 --format="%cd" -- .claude/ docs/harness/
  ```
  가장 최근 날짜가 있는 프로젝트에서 복사해간다. 별도 유지보수 없이 자동으로 정확하다는 게 장점이다.
- **2순위(보조): `docs/harness/HARNESS_LOG.md`** — 여러 저장소를 일일이 열어보지 않고 한눈에 훑어보기 위한 포크 계보 기록. 하네스를 고칠 때마다 적는 게 아니라, **새 프로젝트로 하네스를 포크해갈 때만** "날짜 — 어디서 어디로 포크했는지 — 그 시점 하네스 상태 한 줄 요약"을 추가한다. 세세한 변경 이력은 git 커밋 기록이 이미 갖고 있으므로 중복 기록하지 않는다(둘이 어긋나면 git 기록을 우선한다). **이 파일은 포크할 때 프로젝트마다 새로 시작하지 않고, 이전 프로젝트의 기록 전체를 그대로 들고 가서 이어서 한 줄만 추가한다** — 그래야 어느 사본에서 열어봐도 전체 포크 계보가 한눈에 보인다.

**주의 — 날짜 비교는 "최근"만 알려줄 뿐 "더 많은 내용을 담고 있다"를 보장하지 않는다.** 오래된 사본에서 실수로 하네스를 고쳐 커밋해버리면, 그 순간 커밋 날짜만 보면 최신처럼 보이지만 실제로는 다른 갈래의 개선사항이 빠진 채 갈라진 것이다. 이를 막기 위해:

- **예방(수정 전 필수 확인)**: 어느 프로젝트에서든 하네스(`.claude/`, `docs/harness/`)를 고치기 **시작하기 전에**, 이 프로젝트의 `HARNESS_LOG.md` 마지막 포크 기록을 확인하고, 그 포크 출처 프로젝트가 그 이후 더 앞서 나가지 않았는지(가능하면 그쪽 저장소의 `git log -1` 날짜와 비교) 먼저 점검한다. 뒤처져 있으면 먼저 최신 사본을 받아온 뒤 작업을 시작한다. **출처 저장소에 접근할 수 없는 경우**(다른 컴퓨터에 있거나 이미 지워진 경우 등)에는 최소한 `HARNESS_LOG.md`의 "그 시점 상태 요약"만이라도 참고해, 이 사본 이후로 로그에 다른 갈래의 포크·개선 기록이 더 있는지 확인한다.
- **복구(이미 갈라진 걸 뒤늦게 발견했을 때)**: git이 서로 다른 저장소의 히스토리를 자동으로 합쳐주지 않으므로, 두 사본의 `.claude/`·`docs/harness/`를 직접 `diff`해서(예: `diff -rq harness-A/.claude harness-B/.claude`) 사람이 수동으로 병합한다. 병합이 끝나면 이 사건 자체를 `HARNESS_LOG.md`에 한 줄 남긴다(예: "날짜 — 두 갈래(A, B) 수동 병합 — 원인: 뒤처진 사본에서 수정 후 커밋").

## 7. 하네스를 고치면 곧바로 자체 감사한다

`.claude/agents/`, `.claude/skills/`, `docs/harness/` 중 하나라도 추가·수정하는 작업 라운드가 끝나면, 실행 여부를 묻지 않고 곧바로 `data-harness-auditor`를 실행한다. 이 에이전트는 읽기 전용(보고만 하고 직접 고치지 않음)이라 자동 실행이 안전하다.

- 한 라운드 안에서 여러 하네스 파일을 연달아 고치는 중이라면, 파일마다 돌리지 않고 그 요청이 다 끝난 뒤 한 번 실행한다.
- 감사 결과 발견된 문제를 실제로 고칠지는 항상 사용자 확인을 받은 뒤 진행한다 — 감사 자체는 자동이지만 수정은 자동이 아니다.
- `data-harness-auditor`가 없는 프로젝트로 하네스를 이식했다면(아직 `.claude/agents/`에 포함 안 됐다면), 이 습관을 적용하기 전에 먼저 그 에이전트가 있는지 확인한다.

## 8. 하네스를 별도 브랜치로 분리 관리하기

개인 저장소 하나로 운영하되(1절), 완성본을 공유할 시점엔 하네스(`.claude/`, `docs/harness/`)를 깔끔하게 뺄 수 있어야 하는 경우의 패턴. 저장소를 아예 나누는 대신(1절의 대안), **브랜치로만 분리**한다 — 공유 직전 그 브랜치를 지우면 하네스가 사라진다.

### ⚠️ 흔한 착각 — "브랜치 나누고 `.gitignore`로 가리면 안전하다"는 틀렸다

`.gitignore`는 "추적된 적 없는" 파일에만 적용된다. `.claude/`·`docs/harness/`가 이미 `harness` 브랜치에서 추적 중인 상태라면, `harness` → `main`으로 `git checkout`하는 순간 git은 "현재 브랜치엔 있는데 목표 브랜치엔 없는 추적 파일"로 판단해서 **`.gitignore`와 무관하게 작업 디렉토리에서 그냥 지워버린다.** `.gitignore`는 새 파일이 다시 `git add`되는 것만 막을 뿐, 이미 추적 중인 파일이 브랜치 전환으로 지워지는 건 막지 못한다.

**교훈**: 실제 작업 디렉토리(사용자가 보고 있는 바로 그 폴더)에서 `harness` ↔ `main`을 오가는 `git checkout` 자체를 하지 않아야 한다. 실제 사고 경위(재현 과정, 복구 절차)는 이 프로젝트의 하네스 기록용 Notion 하위 페이지에 남겨둔다 — 특정 세션의 사건 서사는 포터블 문서인 이 파일 대신 그쪽에 둔다.

### 올바른 규칙 — 실제 작업 디렉토리는 항상 `main`, 하네스 편집은 전용 worktree에서만

- **실제 작업 디렉토리(사용자가 보고 작업하는 그 프로젝트 폴더)는 처음부터 끝까지 `main` 브랜치에만 머문다.** 실제 프로젝트 산출물(`ML/`, `app/`, `docs/reports/`, `CLAUDE.md` 등)은 전부 여기서 정상적으로 `main`에 커밋한다. `.claude/`·`docs/harness/`는 `main`의 `.gitignore`에 올려서 git 추적 대상에서 뺀다 — 이 폴더에 물리적으로는 계속 남아있어서 Claude Code가 정상 작동하지만(중요), git이 그걸 `main`에 실수로 다시 커밋하는 일은 막아준다.
- **이 작업 디렉토리에서는 절대 브랜치 전체 전환(`git checkout harness`)을 하지 않는다.** 하네스 파일을 편집·커밋해야 하면 반드시 **전용 worktree 폴더**를 쓴다:
  ```
  git worktree add ../{프로젝트폴더명}-harness-work harness
  ```
  - **네이밍 규칙(포터블)**: worktree 폴더명은 항상 `{프로젝트 폴더명}-harness-work`로 짓는다 — 여러 프로젝트를 나란히 볼 때 "이건 하네스 편집용 worktree구나"를 폴더 목록만 보고 바로 알아보기 위함.
  - 그 폴더 안에서 `.claude/`·`docs/harness/`를 편집하고 `harness` 브랜치에 커밋한다 — **하네스 파일의 실제 편집·커밋은 이 worktree 폴더에서만 한다.**
- **작업 디렉토리(main)는 그 결과를 읽기 전용으로만 동기화받는다** — worktree에서 커밋한 뒤, 작업 디렉토리로 돌아와 경로를 지정한 안전한 checkout으로 최신 내용만 복사해온다(브랜치 전체를 바꾸는 게 아니라서 다른 파일을 지우지 않는다):
  ```
  git checkout harness -- .claude docs/harness
  git reset .claude docs/harness    # main의 스테이징에는 안 올라가게 바로 해제
  ```
- **동기화는 자동/실시간이 아니다** — worktree 폴더와 작업 디렉토리는 파일시스템 차원에서 서로 감시하지 않는, git 이력으로만 연결된 별개의 폴더다. 위 checkout 명령을 실제로 실행해야 반영된다.
  - Claude Code가 worktree에서 직접 하네스를 고쳤다면, 그 작업이 끝나는 즉시 스스로 동기화까지 마친다(사용자가 매번 알려줄 필요 없음).
  - 다른 경로로 하네스가 바뀌었을 가능성이 있으면(다른 세션, 사용자의 직접 수정 등) Claude Code가 자동으로 알 방법이 없으므로, 하네스 관련 작업을 시작하기 전에 최신 상태인지 먼저 확인하는 습관을 들인다. 확실히 하려면 사용자가 알려주는 것도 안전하다.

### 완성본을 공유할 때

`main`이 애초에 하네스를 추적한 적이 없으므로(위 규칙을 지켰다면), 공유 직전엔 `harness` 브랜치만 지우면 끝난다 — `main`은 손댈 필요가 없다:
```
git branch -D harness                    # 로컬에서 하네스 브랜치·이력 제거
git push origin --delete harness         # origin에도 올라가 있었다면 원격에서도 제거
git worktree remove ../{프로젝트폴더명}-harness-work   # worktree 폴더도 정리
```

**과거에 이미 `main`에 하네스가 섞여 들어간 적이 있다면**(이 패턴을 뒤늦게 도입한 경우), `git filter-repo --path .claude --path docs/harness --invert-paths --refs main --force`로 `main`의 과거 커밋 이력까지 제거해야 한다. `filter-repo`는 커밋 해시를 바꾸므로, 이미 origin에 push된 이력이 있었다면 이 작업 뒤 강제 push가 필요하다 — 반드시 사용자 승인 후에만 실행한다(강제 push는 원격 이력을 덮어써서 되돌리기 어렵다). **주의**: `filter-repo`는 재작성 대상 브랜치가 그 순간 체크아웃돼 있으면 작업 디렉토리도 강제로 재체크아웃한다(실제 사고 원인 중 하나) — 반드시 재작성 대상이 아닌 다른 브랜치(예: `harness`)로 전환해둔 뒤 실행한다.

## 9. 새 에이전트를 언제 만들지

**미리 만들어두지 않는다 — 같은 종류의 실수·누락이 실제로 반복되는 걸 확인한 뒤에야 그 실제 사례를 근거로 전담 에이전트를 만든다.** "이런 게 있으면 편리하겠다"는 예측만으로 에이전트를 먼저 만들지 않는다 — 아직 안 겪은 문제를 막으려고 규칙을 쌓으면 정작 실제로 겪는 문제와는 안 맞는 규칙이 되기 쉽고, 하네스만 비대해진다.

- **판단 기준**: 같은 유형의 작업(문서 해석, 문서 검토, 코드 리뷰 등)에서 같은 종류의 실수나 누락이 **서로 다른 시점에 최소 2~3회 이상** 발생했고, 그때마다 사람(메인 세션)이 매번 수작업으로 잡아냈다면 — 그게 전담 에이전트를 만들 신호다.
- **만들 때 반드시 할 것**: 새 에이전트의 계약 문서(`{에이전트명}-contract.md`)에 "근거" 절을 두고, 그 에이전트를 만들게 된 실제 사례(어떤 프로젝트에서 무슨 문제가 몇 번 반복됐는지)를 남긴다 — 나중에 이 에이전트가 왜 존재하는지, 범위를 넓혀야 할지 좁혀야 할지 판단할 근거가 된다.
- **기존 사례**:
  - `CLAUDE.md`의 "요구사항 문서(PDF·스펙 등)를 받으면 메인 세션이 직접 정독한다" 규칙은 이 원칙의 적용 사례다 — 문서 해석용 전담 에이전트를 미리 만들지 않고, "매번 놓치는 부분이 실제로 반복되면 그때 재검토한다"고 명시해뒀다.
  - `planning-doc-qa`(2026-08-21 신설)는 이 원칙에 따라 실제로 만들어진 두 번째 사례다 — `docs/planning/`의 09~11번 ML 문서에서 근거 절 누락·서식 버그·오래된 상호참조가 서로 다른 세 문서에 반복 발생해 매번 메인 세션이 수작업으로 잡아낸 것을 근거로 신설했다(상세는 `docs/harness/planning-doc-qa-contract.md` 6절).

## 10. 병렬화 가능한 작업은 병렬로 — 병렬 서브세션과 전문 에이전트를 함께 오케스트레이션한다

**이 절의 "병렬 서브세션"은 Claude Code의 대화 분기 기능(영문으로 fork라 부름)을 가리키며, 이 문서 1·2·6·8절에서 말하는 "하네스를 다른 프로젝트로 포크한다"(코드/파일 복사)와는 무관한 별개 개념이다** — 같은 문서에 두 "포크"가 섞이면 헷갈리므로 이후로는 항상 "병렬 서브세션"이라 부른다.

이 하네스에는 도메인별 전문 에이전트(전문가 4종, `qa-reviewer`, `stats-advisor`, `data-harness-auditor`, `ml-doc-writer`, `planning-doc-qa`, `report-writer`, `report-qa`, `full-stack-engineer`, `ui-ux-designer`, `design-qa`, `dev-qa` 등 — 2026-08-31 갱신, 통계·실험설계 사전 자문 전담 `stats-advisor` 신설)가 이미 갖춰져 있다 — 순차로 하나씩 처리해도 되는 작업까지 굳이 하나씩 처리하면, 이 오케스트라를 만들어둔 의미가 없어진다. 서로 의존이 없는 작업(예: 같은 상위 결정을 각자 인용만 하는 여러 계획 문서의 캐스케이드 반영)은 병렬로 돌린다.

**"A부터 할까요, B부터 할까요?"처럼 순서를 묻지 않는다 — 두 작업이 건드리는 파일 범위가 겹치지 않으면 기본값은 "둘 다 지금 병렬로"다(2026-08-24 명시 — 파일 범위가 분리된 두 작업을 순차로 처리하다 사용자가 동시 진행이 가능하다고 지적해 확정).** 파일 범위가 겹치는지 스스로 먼저 점검하고(예: 하나는 `ML/`·`app/`, 다른 하나는 `docs/planning/`+Notion처럼 완전히 분리되면 안전), 겹치지 않는다고 판단되면 사용자에게 순서를 묻지 않고 같은 턴에 함께 디스패치한다. 순서를 물어야 하는 경우는 실제로 겹치거나(같은 파일을 두 실행 단위가 동시에 쓰면 충돌), 한쪽 결과가 다른 쪽 입력으로 필요한 진짜 의존관계가 있을 때뿐이다.

**에이전트를 디스패치하려는 순간마다, 지금 논의 중인 그 작업 하나만 볼 게 아니라 `TaskList`를 먼저 열어 다른 대기 중(pending) 작업 중 파일 범위가 안 겹치는 게 있는지 점검한다(2026-08-28 명시).** 위 두 문단은 "사용자가 A·B 두 작업을 동시에 제시했을 때" 순서를 묻지 않는 규칙인데, 실제로는 사용자가 지금 화제로 삼은 작업 하나만 디스패치하고 TaskList에 이미 올라와 있는 다른 독립적인 대기 작업(파일 범위 다름, 담당 에이전트 타입도 다름 — 예: 코드 에이전트가 A를 하는 동안 `ui-ux-designer`는 놀고 있는데 그 사이 처리할 수 있는 디자인 작업이 큐에 있는 경우)은 놓치기 쉽다. 디스패치 직전 `TaskList` 확인을 기계적 체크리스트 항목으로 삼는다 — "지금 대화 주제와 관련 없어 보인다"는 이유로 건너뛰지 않는다.

**근거**: 2026-08-28, SCR-006 중복 참여 감지(코드 작업, `full-stack-engineer`)를 디스패치하면서 같은 순간 `ui-ux-designer`가 완전히 유휴 상태였고 TaskList에는 파일 범위가 전혀 안 겹치는 아티팩트 버전 탭 정리 작업(#17)이 이미 대기 중이었는데도 함께 디스패치하지 않았다. 사용자가 "이런 거 왜 자꾸 놓치냐, 하네스 점검해도 왜 놓치냐"고 지적해, 기존 병렬 디스패치 원칙(위 두 문단)에 "디스패치 직전 TaskList를 반드시 확인한다"는 구체적 실행 절차를 추가했다 — 원칙 자체는 이미 있었지만 "언제 그 원칙을 떠올려야 하는지"에 대한 기계적 트리거가 없어서 반복적으로 놓쳤다.

**"파일 범위가 안 겹친다"는 필요조건일 뿐 충분조건이 아니다 — 한쪽이 "계획·근거 문서를 검증/확정하는" 작업(예: `planning-doc-qa`)이고 다른 쪽이 "그 계획을 실행하는" 전용 에이전트(예: `ml-expert`의 ML 재실행)면, 파일이 안 겹쳐도 병렬로 돌리지 않는다.** 이 실행 역할의 전용 에이전트는 그 실행이 근거로 삼는 계획 문서가 검증·확정되기 **전에는 착수하지 않는다.** 이건 "결과를 보고 나서 방법론을 유리하게 바꾸지 않는다"는 사전 등록 원칙(`ml-project-workflow.md` 11절 2번) 자체는 아니고, 그와 정신은 같지만 별개인 문제다 — **계획 문서가 아직 QA로 수정될 수 있는 상태에서, 그 미확정 내용을 근거로 실행을 시작해버리는 타이밍 문제**다. 계획 문서 QA가 그 문서 내용 자체(수치 계산, 근거)를 고칠 수 있는 상황에서 같은 계획을 참조하는 실행을 동시에 돌리면, 실행이 "곧 수정될지도 모르는 문서" 기준으로 이미 진행돼버려 — QA가 정말 뭔가를 고치면 실행 결과와 확정된 문서가 서로 다른 스펙을 가리키게 된다. 이런 경우엔 계획 QA를 먼저 끝내고(순차), 그 결과가 "문제없음"으로 확정된 뒤에야 실행 역할의 에이전트를 디스패치한다 — 파일 범위 점검(위 문단)에 이 논리적 의존관계 점검을 추가로 통과해야 진짜 병렬 대상이다.

**근거**: 2026-08-25, HPO 3차 재탐색 라운드에서 계획 문서(`10_ML모델링계획서` v1.4, 범위·시도 횟수 근거 포함) QA(`planning-doc-qa`)와 그 계획을 실행하는 `ml-expert`를 파일 범위가 안 겹친다는 이유로 같은 턴에 병렬 디스패치했다가, 사용자가 계획 문서가 확정된 뒤에야 그 기준으로 실행해야 하는 것 아니냐고 지적해 실행 에이전트를 중간에 멈추고 QA 완료를 기다리는 것으로 정정했다.

**병렬 서브세션은 격리된 worktree가 아니라 같은 작업 디렉토리를 공유한다 — 그래서 "파일 범위가 안 겹친다"는 판단이 맞아도, 커밋 시점엔 다른 서브세션이 스테이징해둔 변경분이 우연히 같이 딸려 들어갈 수 있다(2026-08-24 실사고 — 백오피스 문구 수정 커밋에 다른 fork가 편집 중이던 06번 문서 변경분이 섞여 들어감).** `git add <구체적 파일>`로 좁혀 스테이징해도, `git commit`은 파일을 지정하지 않으면 그 순간 스테이징된 모든 것을 커밋한다는 점을 기억한다. 병렬 작업이 진행 중인 상태에서 커밋하기 직전엔 `git status --short` 또는 `git diff --cached --name-only`로 스테이징된 파일 목록이 의도한 것과 정확히 일치하는지 한 번 확인하거나, `git commit -- <파일...>`처럼 커밋 자체를 특정 경로로 제한한다.

**어떤 실행 단위를 쓸지는 작업 성격으로 정한다:**
- **병렬 서브세션(메인 세션의 연장)**: 이 프로젝트에서 "메인 세션 몫"으로 이미 정의된 작업 중, **그 도메인을 담당하는 전용 에이전트가 애초에 없는 경우**(예: `docs/planning/`의 PM 문서 초안 작성·설계 판단 — `CLAUDE.md` 행동 지침이 "PM/AB테스트 워크스트림 문서는 메인 세션이 직접 정독·해석해서 담당한다"고 정하고 있고, `docs/harness/ml-doc-writer-contract.md`의 "역할 경계" 절도 이 문서들을 자신은 건드리지 않는다고 명시한 영역)을 병렬화할 때 쓴다. 대화 맥락을 그대로 물려받으므로 별도 브리핑이 최소화된다.
- **전용 에이전트**: 이미 정형화된 역할(리뷰, 감사, QA, 외부 시스템 반영 등)이 있는 작업은 병렬 서브세션으로 재현하지 않고 그 전용 에이전트를 쓴다 — 그러라고 도메인별로 나눠 만든 것이다. **메인 세션이 원래 직접 하던 도메인 작업(예: ML 파이프라인 노트북 작성)이 이미 있는 도메인 전문가 에이전트(`ml-expert`·`pandas-expert`·`dl-expert`·`sql-expert`)의 전문 영역과 겹치면, 병렬 서브세션(fork)보다 그 전문가 에이전트를 우선한다** — 에이전트가 실제 작업 경험을 쌓아 더 전문화되도록 계속 실전에 투입하는 게 이 하네스의 목적이기 때문이다(2026-08-24 사용자 지적 — 도메인 전문가 에이전트를 실전에 지속적으로 투입해 전문성을 키워가는 것이 애초에 이 하네스를 만든 목적이라는 점을 재확인시킴).
  - **구체적 라우팅 예시 — `analysis/`(AB테스트·백오피스·백엔드 데이터에 대한 판다스 결과 분석 노트북, 옛 이름은 `app/` 안이었으나 2026-08-31 별도 폴더로 분리)는 `pandas-expert` 담당이다.** classical ML 모델링이 아니므로 `ml-expert`도 아니고, "메인 세션이 이미 맥락을 파악하고 있어 직접 하는 게 빠르다"는 이유로 fork로 직접 작성하지도 않는다(2026-08-31 실사고 — `app/21_ux_result_analysis.ipynb`를 메인 세션이 fork로 직접 만들면서, 노트북에 SVG 인사이트 카드·라이브러리 차트를 넣는 `ml-project-workflow.md` 14절·`notebook-toolkit` 컨벤션 적용을 빠뜨렸다. 이 컨벤션은 `ML/` 폴더 노트북에만 국한된 게 아니라 이 프로젝트의 모든 노트북에 적용되는데, 전담 전문가가 아닌 fork로 직접 만들다 보니 놓쳤다 — 사용자가 지적하고서야 원래 `pandas-expert`가 담당했어야 할 작업임을 인지했다). **AB테스트뿐 아니라 백오피스·백엔드 데이터 분석 전반도 이 라우팅 대상이다** — `pandas-expert.md`의 "`analysis/`는 `ML/`과 같은 수준의 엄밀함으로 작업한다" 절을 참고해, ML 파이프라인 작업을 거치며 올라간 이 프로젝트의 완성도 기준(SVG 인사이트 카드, `stats-advisor` 사전 자문, `qa-reviewer` 사후 검증)을 그대로 적용한다. **`analysis/`·`app/`은 이 프로젝트 고유 폴더명이다** — 하네스를 다른 프로젝트로 포크했다면 그 프로젝트의 `CLAUDE.md` 폴더 구조에서 "classical ML 파이프라인이 아닌 판다스 결과 분석"이 실제로 어느 폴더에 있는지 먼저 확인하고, 그 프로젝트에 아직 그런 폴더가 없다면 "새 폴더로 분리할지"를 이 절의 판단 원칙(fork보다 전문 에이전트 우선, ML급 엄밀함 적용)만 이식해서 새로 정한다 — 폴더명 자체를 그대로 복사해오지 않는다.
  - **전문가 에이전트는 힌트 전용이 아니다** — `docs/harness/expert-contract.md`에 따르면 사용자가 스스로 막힌 부분에 대한 도움만 요청했을 때만 힌트 모드로 전환하고, **명시적으로 "완성해서 작성해줘" 같은 전체 구현을 요청하면 실행 가능한 완성 코드/노트북을 직접 쓴다.** 전문가 에이전트를 실행 작업에 쓸 때는 프롬프트에 "이건 힌트 요청이 아니라 명시적으로 요청하는 전체 구현"이라고 분명히 밝혀서, 스스로 힌트 모드로 오판하지 않게 한다.
- **전형적 패턴(초안과 검증을 같은 실행 단위에 섞지 않는다)**: 병렬 서브세션들이 동시에 초안을 만들고 로컬 커밋까지 마친 뒤, 그 라운드가 끝나면 전용 검증·반영 에이전트(`planning-doc-qa`, `data-harness-auditor` 등)를 한 번에 실행해 검토·수정·외부 반영(Notion 등)을 맡긴다. 초안 단계에서 검증까지 함께 시키면 그 전용 에이전트가 정작 실행돼야 할 시점(라운드가 다 끝난 뒤, 한 번에)을 놓치게 된다.
- **자동 트리거 조건(하네스 수정 후 감사, 문서 버전업 후 QA 등)이 충족되면 그 즉시 디스패치한다 — "나중에 해야지"라고 미루지 않는다.** 이 판단-없는 기계적 체인을 왜 fork/에이전트로 즉시 돌려야 하는지의 근거는 `karpathy_skills.md`의 "바이브 코딩 실천 규칙"에 정리해뒀다(중복 설명 안 함). **이 원칙은 "지금 바로 디스패치할 수 있는 것"에 한정된다** — 지금 다른 에이전트가 관련 파일을 붙잡고 있어 아직 디스패치할 수 없는, "그 작업 끝나면 이어서 하겠다"는 미래 약속은 이 원칙이 커버하지 못한다(디스패치 자체를 아직 못 하므로 "즉시 디스패치"가 적용될 대상이 없다) — 그 경우는 아래 11절을 따른다.

**이 절은 git/GitHub 작업에 국한되지 않는 상시 원칙이다** — 이 문서(`git-workflow.md`)는 `CLAUDE.md`에서 `@docs/harness/git-workflow.md` 형태로 참조돼 있어 매 세션 컨텍스트에 항상 로드된다. `CLAUDE.md`가 이 파일을 "저장소 구조·원격 연결을 정리할 때" 참고하라고 안내하는 문구는 9절까지의 git 특화 절차에 해당하는 것이고, 이 10절은 작업 방식 전반에 적용된다.

**근거**: 2026-08-22, 사용자가 병렬 작업을 충분히 활용하지 않고 있다는 점과, 다양한 전문 에이전트를 만든 목적 자체가 오케스트레이션을 통해 그것들을 적극 활용하는 데 있다는 점을 지적한 것을 계기로 신설. 그 시점까지는 병렬 서브세션을 쓸 수 있다는 것 자체는 알고 있었지만, "언제 병렬 서브세션을 쓰고 언제 전용 에이전트로 넘겨야 하는지"에 대한 명시적 기준이 하네스에 없었다.

## 11. 동시에 여러 에이전트를 굴리는 세션에서는 "다음에 할 일"을 채팅 텍스트가 아니라 `TaskCreate`/`TaskUpdate`로 관리한다

**이 절은 10절의 "즉시 디스패치" 원칙과 짝을 이루지만 다른 문제를 다룬다** — 10절은 "지금 바로 디스패치할 수 있는 작업을 미루지 않는 것"이고, 이 11절은 "지금은 다른 에이전트가 관련 파일을 붙잡고 있어 아직 디스패치할 수 없는, 채팅으로만 한 미래 약속을 놓치지 않는 것"이다. 후자는 애초에 "즉시 디스패치"할 대상 자체가 없으므로 10절의 구조적 안전장치(포크는 알림이 오므로 안 잊힌다)가 적용되지 않는다.

**여러 에이전트를 병렬로 굴리는 긴 세션에서 "이건 지금 하는 작업 끝나면 이어서 할게요" 같은 약속을 채팅 응답 텍스트로만 남기면, 그 약속이 대화가 길어지고 새 긴급 요청(버그 등)이 계속 끼어드는 사이 조용히 잊힌다.** 원인은 다음과 같은 구조적 문제다 — 채팅 프로즈 안의 "큐"는 (1) 검색·체크가 안 되고, (2) 다음 긴급 요청이 들어오면 그 처리에 컨텍스트가 쏠려 이전 약속을 다시 꺼내볼 계기가 없으며, (3) 컨텍스트가 컴팩션되면 요약 과정에서 디테일이 흐려질 위험도 있다. 반면 새 요청이 들어와도 "지금 하는 것"에만 반응하고 "이전에 하겠다고 해놓고 안 한 것"을 스스로 재확인하는 습관이 없으면, 사용자가 먼저 물어봐야만 그제서야 처리하게 된다 — 이건 사용자 입장에서 "매번 같은 걸 다시 말해야 하는" 신뢰 저하로 이어진다.

- **여러 에이전트를 동시에 굴리기 시작하는 시점부터 `TaskCreate`로 실제 작업 큐를 만든다** — "나중에 이어서 하겠다"고 채팅에 적은 각 항목은 그 즉시 태스크로도 만든다(채팅 응답과 태스크 생성을 같은 턴에 함께 한다, 나중으로 미루지 않는다). 각 태스크의 `metadata`에 담당 에이전트 ID를 남겨두면, 나중에 그 에이전트가 완료 알림을 보낼 때 어떤 태스크가 끝난 건지 바로 대응시킬 수 있다.
- **(2026-08-28 명시) "나중에 하겠다"고 스스로 약속한 것뿐 아니라, 사용자가 새로 지시한 할 일 자체도 받는 즉시 태스크로 만든다.** 지금 다른 에이전트가 관련 작업을 하고 있어 바로 착수하지 못하고 큐에 넣어야 하는 상황이면 특히 그렇다 — "지금 하는 것 끝나면 이어서 하겠다"는 응답을 채팅으로만 하고 `TaskCreate`를 빠뜨리면, 정확히 위에서 설명한 것과 같은 방식으로 그 지시 자체가 잊힌다. 사용자의 지시를 받은 그 턴 안에서 태스크 생성까지 마친다(응답하고 나중에 만드는 게 아니라 응답과 함께 만든다).
- **에이전트가 작업을 시작하면 해당 태스크를 `in_progress`로, 완료·검증까지 마치면 `completed`로 갱신한다** — "코드는 짜졌지만 검증 전"인 상태를 `completed`로 표시하지 않는다(`TaskUpdate` 도구 자체의 규칙과 동일).
- **새 긴급 요청을 처리하기 전에, 또는 한 라운드의 작업이 끝나 다음에 뭘 할지 판단해야 할 때마다 `TaskList`로 먼저 확인하는 습관을 들인다** — "지금 뭐 하고 있었지"를 기억에만 의존하지 않는다. 시스템이 "Task tools를 최근에 안 썼다"는 리마인더를 보내면, 그건 정확히 이 상황(할 일이 쌓여있는데 구조화된 추적 없이 채팅 기억에만 의존하는 상황)을 가리키는 신호로 받아들인다 — 무시하지 않는다.
- **사용자가 "지금 하고 있는 것과 할 것 정리해줘"라고 물으면, 채팅 기록을 거슬러 올라가 재구성하지 않고 `TaskList`를 조회해서 답한다** — 태스크 목록 자체가 그 질문에 대한 신뢰할 수 있는 단일 출처(source of truth)가 되게 한다.

**근거**: 2026-08-27~28, 사용자가 Claude Artifact에 "최신 버전" 탭을 추가해달라고 요청했고, "3품목 콘텐츠 구현이 끝나면 이어서 하겠다"고 채팅으로 약속했다 — 그 사이 SCR-004 버그 수정 여러 라운드, 바텀시트 타이밍 조정, 하네스 작업(TRD·dev-qa 신설) 등 다른 작업이 계속 끼어들면서 그 약속이 방치됐고, 사용자가 "왜 자꾸 내가 말한 거나 할 일을 놓치냐"고 직접 지적한 뒤에야 처리됐다. 이 세션에서 시스템이 여러 차례 `TaskCreate`/`TaskUpdate` 사용을 권장하는 리마인더를 보냈는데도 계속 무시하고 있었다는 게 근본 원인으로 확인됐다.
