# 버그 이슈 로그 (재사용 가능한 패턴)

증상을 기준으로 과거 버그를 찾아볼 수 있는 참고 전용 로그다. 이 프로젝트(또는 다른 프로젝트)의 워크플로우 문서(`ab-test-app-workflow.md` 등)는 "앞으로 이렇게 코딩해라"는 처방만 간결하게 담고, 이 문서는 "무엇을 시도했고 어떻게 틀렸고 최종 원인이 뭐였는지"를 시간순으로 상세히 담는다 — 처방과 진단 서사를 분리해 규칙 문서는 간결하게 유지하면서, 비슷한 증상이 재발했을 때 과거 시행착오를 빠르게 훑어볼 수 있게 한다.

`git-workflow.md` 2절의 "이식 대상(그대로 재사용)" 목록에 해당한다 — 다른 프로젝트로 하네스를 포크할 때 이 문서도 그대로 복사해간다. 여기 담긴 사건들은 특정 프로젝트(예: 이 Mercari 프로젝트)의 구체적 코드를 인용하지만, 새 프로젝트에서 완전히 다른 스택(다른 앱·웹)을 다루더라도 "이런 종류의 증상은 이런 함정에 잘 빠진다"는 진단 패턴 자체는 참고할 가치가 있다.

## 언제 항목을 추가하나

- 원칙: 버그가 완전히 해결되고 최종 원인이 확정된 뒤에 추가한다.
- 예외: 진단이 여러 차례 틀렸다가 마침내 해결되는 것처럼 "시행착오 자체가 교훈"인 사례는, 조사가 끝나기 전이라도 상태를 "조사 중"으로 먼저 등록해두고 결론이 나면 갱신한다 — 시행착오 과정 자체(무엇을 의심했다가 왜 틀렸는지)가 다음번 진단 속도를 높여주는 핵심 정보이기 때문이다.
- 이미 워크플로우 문서에 "근거"로 짧게 기록된 사건이라도, 그 사건이 여러 차례 재발했거나 진단이 여러 번 틀렸다면 이 로그에도 증상 중심으로 별도 항목을 남긴다 — 목적(처방 근거 vs 증상 검색)이 다르므로 같은 사건이 양쪽에 있어도 중복이 아니다.

## 항목 형식

```
### {한 줄 증상 요약} (상태: 조사 중 / 해결됨 — 필요시 "실기기 재확인 대기" 등 조건부 표시 추가)
- **환경**: 어느 플랫폼·브라우저·스택에서 재현됐는지
- **잘못된 진단 1, 2, ...**: 시도했다가 틀렸던 원인 추정과, 왜 틀렸는지 밝혀진 이유를 시간순으로 하나씩 번호를 매겨 적는다(오진단이 하나뿐이면 "잘못된 진단"으로 단수 표기해도 된다) — 각 진단이 왜 그럴듯해 보였는지, 무엇으로 반박됐는지까지 남겨야 다음번에 같은 함정에 안 빠진다.
- **최종 원인**: 확정된 근본 원인(해결 전이면 "미확정, 조사 중")
- **해결 방법**: 실제로 적용한 수정 — 특정 프로젝트 코드보다 "왜 이렇게 고쳐야 하는지"라는 일반 원칙 위주로 적어야 다른 스택에서도 참고할 수 있다
- **교훈**: 다음에 비슷한 증상을 만났을 때 먼저 의심해봐야 할 것(여러 개면 번호를 매겨도 된다). 아직 해결 전이라 잠정적인 교훈이면 "교훈(잠정)"으로 표시하고, 해결되면 괄호를 뗀다.
```

## 로그

### 모바일에서 CTA 버튼 아래 하단에 불필요한 여백/클리핑이 생김 (상태: 해결됨 — 실기기 재확인 대기)

**주의 — 이 항목은 원래 "찌그러짐"과 한 항목으로 묶여 있었으나, 조사 결과 완전히 다른 두 원인으로 밝혀져 분리했다.** 찌그러짐 증상은 바로 아래 별도 항목을 참고한다.

- **환경**: 카카오톡 인앱 브라우저(안드로이드, 갤럭시 플립)에서 처음 발견 → 이후 아이폰 Chrome, 갤럭시 Chrome(일반)에서도 재현 → 데스크톱 웹 브라우저(키보드가 전혀 없는 환경)에서도 동일 증상 재현 확인 → **Playwright(Chromium·WebKit, 여러 데스크톱 창 크기)로 확정 재현.**
- **잘못된 진단 1**: 키보드 열림을 판정하는 로직이 `innerHeight - visualViewport.height < 40`처럼 특정 기기(갤럭시 플립) 하나에서 관찰된 40px을 하드코딩된 임계값으로 쓰고 있었다 — 이 값이 다른 브라우저에 안 맞아 오판정이 난다고 보고, "자기 자신의 직전 실측값과 상대비교"하는 방식으로 교체했다. 일부 모바일 브라우저에서는 개선됐지만 근본 해결은 아니었다.
- **잘못된 진단 2**: 데스크톱 웹(키보드가 아예 없는 환경)에서도 같은 증상이 재현되는 게 확인되면서, 애초에 "키보드 열림 판정 로직" 자체가 원인이 아니었을 가능성이 크다는 게 드러났다. 다음 의심 대상으로 "화면을 프레임에 맞춰 축소·확대하는 `fitHeight()` 계산 로직 자체(정적 상태)"를 지목했으나, **이것도 실제 원인이 아니었다** — grep으로 코드를 추적하는 것만으로는 실제 DOM 치수를 알 수 없어, 두 번째로 잘못된 추측을 할 뻔했다.
- **최종 원인**: 두 진단 모두 틀렸다. 실제 원인은 뷰포트 계산과 완전히 무관한 **정적 레이아웃 오버플로**였다 — 바텀시트 안 스크롤 컨테이너(`.p3-scroll`, `clientHeight` 501px)가, 선택 카드(`.p3-decision`)가 펼쳐진 뒤의 실제 콘텐츠 높이(`scrollHeight` 651px)를 담기엔 150px 부족했다. 시각적으로는 `max-height` 캡이 여유 있어 다 펼쳐진 것처럼 보이지만, 그 결과 "다음 보기" CTA 버튼이 폰 프레임의 클리핑 경계(`overflow:hidden`) 밖으로 밀려났다 — 사용자가 본 "검은 여백"은 사실 이 클리핑 경계였다. 모바일 키보드가 열리면 그 위에 또 겹쳐서 더 심하게 보였을 뿐, 키보드 유무와 무관하게 항상 존재하던 버그다.
- **해결 방법**: 코드 추적(grep)만으로는 실제 DOM 치수(`scrollHeight` vs `clientHeight`)를 알 수 없었다 — Playwright로 브라우저를 직접 열어 문제가 된 요소들의 실측 치수를 콘솔에서 확인하고 나서야 진짜 원인을 찾았다. 수정 자체는 이미 있던 방어 로직(입력창 포커스 시 CTA를 스크롤해 보여주는 함수)을 "선택 카드가 펼쳐지는" 이벤트에도 재사용하도록 확장한 것으로, 새 로직을 만들 필요 없이 기존 코드를 다른 트리거에도 연결하는 선에서 끝났다.
- **교훈**: 이 사건이 완전히 해결된 뒤 정리한 확정 교훈이다. (1) **"모바일 전용처럼 보이는" 레이아웃 버그도 데스크톱 브라우저에서 먼저 재현을 시도해보면 진단 범위를 빠르게 좁힐 수 있다** — 처음부터 "실기기 전용"이라고 단정하고 플랫폼별 로직(키보드 판정 등)만 의심하면 플랫폼과 무관한 원인을 놓친다. (2) **"검은 여백/찌그러짐" 같은 시각적 증상은 원인 후보가 여러 겹(뷰포트 계산, 스케일 계산, 레이아웃 오버플로 등)일 수 있고, 실제로는 서로 다른 두 개의 독립된 버그일 수도 있다 — 겉보기 증상이 비슷하다고 같은 원인, 심지어 같은 버그라고 가정하지 않는다.** (3) **grep 기반 코드 추적은 "코드가 무엇을 하려고 하는지"는 보여주지만 "실제로 화면에 얼마의 치수가 나오는지"는 안 보여준다** — 정적 레이아웃 버그를 의심할 땐 코드를 읽는 것보다 먼저 Playwright 등으로 실제 DOM 치수(`scrollHeight`/`clientHeight` 등)를 찍어보는 게 훨씬 빠르게 원인을 좁혀준다.

### 짧은(693px 미만) 화면에서 모바일 화면이 세로로 눌려 보임(찌그러짐) (상태: 해결됨 — 실기기 재확인 대기)

- **환경**: 위 CTA 여백 버그와 같은 상황에서 함께 보고됐다 — 짧은 화면(카카오 인앱, 일부 데스크톱 창 크기 등 693px 미만 높이)에서만 재현.
- **잘못된 전제**: 위 CTA 여백 버그와 같은 원인일 것이라고 가정하고 함께 조사했다 — 실제로는 완전히 다른, 독립된 버그였다(교훈은 위 항목 참고).
- **최종 원인**: `fitHeight()`가 화면 전체를 감싸는 최상위 프레임(`.proto-frame-outer`)에 `scaleY(...)`만 적용해 **세로축만 압축**하고 있었다 — Playwright로 `getComputedStyle().transform` matrix를 `scaleX = √(a²+b²)`, `scaleY = √(c²+d²)`로 직접 분해해 확인: 693px보다 짧은 모든 뷰포트에서 `scaleX=1`인데 `scaleY`만 0.79~0.94로 떨어짐. 코드 주석에 남아있듯, 원래 가로세로를 동일 비율로 압축(`scale()`)했다가 "좌우에 검은 여백(레터박싱)이 생긴다"는 실기기 버그가 나서 세로 단독 압축으로 바꾼 전례가 있었다 — 즉 **"찌그러짐 없음"과 "좌우 여백 없음"이 서로 트레이드오프 관계인 설계**였고, 지금 코드는 후자를 택해 찌그러짐을 대가로 치르고 있었다.
- **처음 제시했던(반려된) 해결 방향**: 이 트레이드오프의 반대쪽(균일 `scale()`로 되돌려 좌우 여백을 감수)이나 부분 CSS 완화안을 옵션으로 제시했으나, 사용자가 "근본을 해결해야지, 반응형에 최적화해야 한다 — 애초에 구현할 때부터 고려했어야 한다"며 명시적으로 반려했다 — **"두 결함 중 하나를 고른다"는 프레이밍 자체가 잘못됐다는 지적**이었다.
- **최종 해결 방법**: JS가 뷰포트 높이를 읽어 프레임 전체를 스케일 변형하는 방식 자체를 버리고, **CSS가 프레임 높이 자체를 `min(693px, 100dvh)`로 정직하게 줄이고, 짧아진 만큼은 화면별로 이미 있는 내부 스크롤 영역이 자연스럽게 흡수**하게 한다 — 위 CTA 여백 버그를 고칠 때 쓴 "넘치면 스크롤로 흡수한다"는 원리를 프레임 레벨로 확장한 것이다. 변경 범위는 CSS 한 줄 + JS 함수 안 6줄(스케일 적용 부분만 제거, 키보드 판정 로직이 의존하는 나머지 상태 갱신 코드는 그대로 유지)로 최소화했다.
- **검증(Playwright)**: (1) 5개 뷰포트에서 `getComputedStyle().transform`이 전부 `none`으로 나와 scaleX=scaleY=1이 항상 보장됨을 재확인. (2) CTA 가시성도 3개 뷰포트 전부 정상 — 프레임이 CSS로 실제로 줄어드니 내부 스크롤 컨테이너의 `clientHeight`도 정직하게 함께 줄고, 기존 `scrollToRevealCta()`가 그 값을 기준으로 여전히 정확히 동작해 이전 수정과 자연스럽게 맞물렸다. (3) 이 프로젝트에서 가장 위험도 높았던 공유 지점(SCR-004 "기타" 모달 + 키보드)을 Android 스타일(레이아웃 뷰포트 실제 축소)·iOS 스타일(`visualViewport`만 변화) 두 시나리오로 각각 재현 — 두 경우 모두 기존 키보드 감지 로직이 원래 설계 의도대로 정확히 분기(Android는 프레임이 이미 CSS로 줄어 모달을 추가로 밀 필요 없음, iOS는 레이아웃이 안 줄었으니 모달을 밀어올림)해 상호작용이 손상되지 않았음을 확인. (4) grep 회귀 스윕(뷰포트 판정 11곳, 체크 아이콘, 스켈레톤 체인, 2단계 타이밍값)도 전부 불변 확인.
- **부수 효과**: `fitHeight()`가 스케일을 적용하는 게 아니라는 사실과 어긋나 있던 stale 주석 8곳도 함께 정정했다 — 그중 3곳은 단순 표현이 아니라 "프레임이 이미 재계산됐다"는 틀린 전제를 담고 있어, 방치했으면 다음 세션이 코드를 오독할 뻔했다.
- **교훈**: (1) **"두 가지 결함 중 하나를 고르라"는 질문을 받으면, 그 질문의 전제(왜 이 둘이 서로 배타적인지) 자체를 의심해본다** — 이 사례에서는 "고정 크기 화면을 JS로 강제 변형한다"는 원래 접근 방식 자체가 트레이드오프를 만들어낸 원인이었고, 그 접근 자체를 버리자 트레이드오프가 통째로 사라졌다. (2) 레이아웃을 반응형으로 만드는 결정은 버그가 생긴 뒤 사후에 고민하기보다, 애초에 화면을 구현하는 시점에 "고정 크기를 가정하고 나중에 스케일로 맞출 것인가, 처음부터 유동적으로 짤 것인가"를 미리 정해두는 게 낫다.

### 갤럭시 Z 플립 크롬에서 희망가 입력 중 화면(바텀시트 스크롤)이 튕김 (상태: 해결됨 — 실기기 재확인 대기)

- **환경**: 갤럭시 Z 플립 크롬(같은 기기의 카카오 인앱 브라우저는 정상) — 희망가 입력란(SCR-002/003 "아니요" 선택 후 노출되는 가격 입력창)에 포커스가 들어가 키보드가 열리는 도중.
- **혼동하기 쉬운 전제**: 이 항목 위의 "짧은 화면 찌그러짐" 버그를 고치며 이미 "포커스 중엔 `__layoutHeightBaseline`을 절대 갱신하지 않는다"는 원칙을 세워 다른 키보드 관련 버그(SCR-004 "기타" 모달의 검은 여백)를 해결한 전례가 있어, 이번 "튕김"도 그 수정이 회귀했거나 그 원칙이 안 지켜지는 곳이 있을 거라고 먼저 의심했다. 실제로 코드를 재추적해보니 `__layoutHeightBaseline` 갱신 지점은 여전히 단 한 곳(`fitHeight()`의 포커스 없음 분기)뿐이었고, 그 원칙은 전혀 깨지지 않은 채 정상 작동 중이었다 — **원인은 그 수정이 애초에 커버하지 않는 완전히 다른 코드 경로였다.**
- **최종 원인**: 희망가 입력란 전용 키보드 감지 함수(`priceInputKbCheck`)는 `__hasLayoutViewportShrunk()`(위에서 고정된 그 기준선)와는 별개로, 포커스 시점에 캡처한 `priceInputKbBaselineHeight`(고정되지 않음) 대비 `shrink > 100px`이면 "열림"(CTA를 보이게 스크롤), 아니면 "닫힘"(스크롤을 원위치로 되돌림) 두 분기로 나뉘어 있었다. 키보드가 열리는 애니메이션은 물리적으로 shrink가 0에서 시작해 점점 커지므로 반드시 0~99px 구간을 거쳐가는데, 이 구간에서는 (아직 한 번도 열린 적이 없어도) "닫힘" 분기가 매번 실행돼 스크롤을 원위치로 되돌렸다가, shrink가 100px을 넘는 순간 "열림" 분기로 넘어가며 다시 위로 튀어 올랐다 — 지터가 있어야만 나는 문제가 아니라, **지터 없는 완전히 단조 감소하는(900→860→820→780→...px) 정상적인 키보드 오픈 궤적만으로도** Playwright(`page.setViewportSize`를 연속 호출해 `visualViewport.resize` 이벤트를 실측)로 재현됐다(수정 전 `.p3-scroll.scrollTop` 추이에서 방향 반전 1회 확정 관찰).
- **해결 방법**: (1) "실제로 열림으로 한 번이라도 분류된 적 있는가"를 추적하는 플래그(`priceInputKbHasOpened`)를 추가해, 아직 한 번도 열린 적 없는 초반 저-shrink 프레임에서는 "닫힘" 분기가 아예 아무 것도 하지 않게 가드했다(되돌릴 "열린 상태" 자체가 없으므로). (2) 열림·닫힘에 히스테리시스(열림=100px, 닫힘=60px, 그 사이는 데드존)를 추가해, 실기기에서 100px 경계 근처를 여러 번 오가는 진짜 지터가 있어도 매번 왔다갔다 반응하지 않게 했다 — 이 부분은 Playwright로 100px 경계를 넘나드는 인위적 지터 시퀀스를 만들어 수정 전(방향 반전 3회) → 수정 후(0회)로 재확인했다.
- **검증**: Playwright로 (1) 단조 감소 시퀀스, (2) 경계 근처 지터 시퀀스, (3) 진짜 열림→데드존 잔떨림→진짜 닫힘→진짜 재열림까지 포함한 풀 사이클, (4) 전체 참여자 플로우(화면1→가격화면A→가격화면B(희망가 입력 포함)→SCR-004→"기타" 모달) e2e를 각각 실행해 콘솔/페이지 에러 0건, `scrollTop` 방향 반전 0회를 확인했다. 로컬 정적 문법 검사(`new Function()`)로 스크립트 블록 손상 여부도 재확인했다.
- **범위 밖으로 남긴 것 → 2026-08-27 후속 조치로 예방적 적용 완료**: SCR-004 "기타" 모달·설문 "기타" 입력의 키보드 감지 함수(`checkKeyboardOpen`, 인스턴스 2곳)·`pv4CheckKeyboardOpen`은 같은 100px 임계값 패턴을 쓰지만, Android 스타일(`layoutShrunk=true`)에서는 `!layoutShrunk` 게이트로 애초에 클래스 토글 자체가 비활성화되는 구조라 갤럭시 플립(Android) 환경에서 이 함수가 튕김에 기여할 가능성은 낮다고 처음엔 판단했다(실제 재현·수정은 안 함, 코드 분석뿐). 이후 코디네이터 지시로, 실제 버그 재현 없이도 "같은 파일에서 같은 계열의 키보드 타이밍 경합이 함수마다 따로따로 터진 전례"를 근거로 이 세 함수 모두에 `priceInputKbCheck`와 동일한 히스테리시스(열림=100px·닫힘=60px, 상태 변수로 데드존 유지, `layoutShrunk`일 때만 즉시 강제 닫힘 — "열린 적 있는가" 플래그는 이 함수들엔 부수효과가 없는 순수 클래스 토글이라 불필요해 안 넣음)를 예방적으로 적용했다. Playwright로 (a) 100px 경계 순수 지터 시퀀스에서 토글 0회(수정 전이었다면 여러 번 뒤집혔을 시나리오), (b) 실제 열림→데드존→진짜 닫힘→재열림 전이가 정확히 예상대로 일어나는지 프로토뷰어(`pv4`)·갤러리 두 인스턴스(`s4`·`s4b`, 독립된 페이지에서 격리 재현) 모두 확인 — 회귀 스윕(플립4 튕김 재검증·전체 e2e 플로우 WebKit/Chromium·마진 버그 재검증 12회)도 전부 통과.
- **교훈**: (1) **"이전에 이미 고친 것과 증상이 비슷하다"고 해서 그 수정이 회귀했다고 먼저 의심하지 않는다** — 같은 파일 안에 구조가 비슷해 보이는 여러 개의 독립된 코드 경로(이 경우 `fitHeight()`의 baseline 로직 vs `priceInputKbCheck`의 자체 baseline/threshold 로직)가 나란히 있을 수 있고, 하나를 고쳤다고 나머지가 자동으로 안전해지는 게 아니다 — 이전 수정이 실제로 그대로 남아있는지부터 확인한 뒤에도 재현되면, "커버 범위 밖의 다른 경로"를 찾는다. (2) **"열림/닫힘"처럼 상태가 왔다갔다하는 로직을 raw 값과 단일 임계값 하나로만 판정하면, 그 값이 임계값을 향해 다가가는 정상적인 궤적 자체가(지터 없이도) 오분류·되돌림을 유발할 수 있다** — "이미 그 상태로 분류된 적이 있는가"라는 이력(hysteresis/latch)을 함께 두지 않으면, 대칭적으로 보이는 open/close 코드가 실제로는 비대칭적인 부작용(한쪽은 부수효과 없음, 다른 쪽은 스크롤 리셋 같은 실제 DOM 변경)을 낼 때 특히 위험하다.

### 아이폰 실기기 "키패드 마진 버그" 간헐적 재발 — 포커스 전 scrollTop 캡처 시점의 이중 경합 (상태: 해결됨 — 실기기 재확인 대기)

- **환경**: 아이폰(14 Pro·17, 카카오·크롬 — 실기기에서 이미 해결 확인됐던 화면이 재발). Playwright WebKit 엔진으로 100% 정밀 재현·수정.
- **혼동하기 쉬운 전제**: 코디네이터가 처음 지목한 용의선은 "바로 위 항목(갤럭시 Z 플립 크롬 튕김)을 고치며 추가한 `priceInputKbCheck`의 히스테리시스(`priceInputKbHasOpened`)가 iOS 분기(`scrollToRevealCtaForKeyboard()` 등)의 조건이나 상태 변수를 실수로 공유해버린 게 아니냐"는 것이었다. 코드 재검토 결과 그 의심은 틀렸다 — `priceInputKbHasOpened`는 두 플랫폼 분기 모두에서 의도적으로 공유되는 이력 플래그일 뿐이고, iOS 전용 로직(`scrollToRevealCtaForKeyboard()`) 자체는 그 수정에서 단 한 줄도 안 바뀌었다. WebKit으로 "키보드가 열려있는 동안 CTA가 가려지는지"만 20회 반복 검증해도 0/20으로 항상 정상이었다 — 즉 **문제는 열려있는 동안이 아니라, 키보드가 닫힌 뒤(blur) 복귀하는 목표값 자체가 잘못 캡처되는 데 있었다.**
- **최종 원인(세 겹)**: `priceInputPreKbScrollTop`(키보드가 닫힐 때 되돌아갈 스크롤 목표값)을 `focus` 이벤트 리스너 "안"에서 읽고 있었는데, 그 시점엔 이미 늦은 경우가 있었다 — Playwright WebKit 정밀 추적(10~20ms 간격 폴링 + `scrollTo()` 호출 로깅)으로 시간순으로 세 가지 서로 다른 오염 지점을 찾아냈다.
  1. **가장 이른 지점**: 핸들 탭으로 바텀시트 결정 영역이 펼쳐질 때(`revealNow()`) 그 자신의 지연된 스크롤 보정(`scrollToRevealCta()`, 420ms 뒤 호출)이 실제로 안정되기까지 최대 ~690ms 걸리는데, 그 전에 "아니요"가 눌리면 "아직 안정 안 된" 중간값이 그대로 캡처됐다.
  2. **두 번째 지점**: (1)이 이미 안정된 뒤라도, "아니요" 클릭이 트리거하는 `selectChoice('no')`의 CSS 트랜지션(희망가 입력란 `max-height` 등)이 WebKit의 스크롤 앵커링(레이아웃이 바뀔 때 시각적 점프를 막으려 브라우저가 자동으로 scrollTop을 보정하는 기능)을 건드려 scrollTop이 값 하나로 "가라앉은 채"(실측: 198→66, 자연 복귀 없음) 굳어버렸다 — **B안(범위가) 화면에서만** 재현되고 A안(단일가)에서는 재현되지 않았다(정확한 이유는 미확정 — 두 화면의 레이아웃 차이가 스크롤 앵커링의 판단에 영향을 주는 것으로 추정).
  3. **세 번째 지점(실제 포커스 자체)**: WebKit은 입력란에 포커스가 들어갈 때 그 입력란을 화면에 보이게 하려는 자체 네이티브 스크롤을 갖고 있는데, 이게 우리 JS의 `focus` 리스너가 실행되기도 "전에" 이미 끝나 있는 경우가 있었다.
  세 지점 모두 "focus 리스너 안에서 아무리 빨리 읽어도 늦다"는 공통점이 있어, 유일하게 확실한 해법은 **이런 부작용을 일으키는 어떤 코드보다도 먼저** 캡처해두는 것이었다.
- **해결 방법**: (1) `revealNow()`가 시작하는 지연 스크롤이 정말로 끝났는지 추적하는 플래그(`revealScrollSettled`)를 두고, "아니요" 클릭 핸들러가 이 값이 true가 될 때까지(단, 안 끝났으면 캡처·`selectChoice` 자체를 살짝 미룬다) 기다린다. (2) 캡처(`capturePriceInputPreKbScrollTop()`)를 `selectChoice('no')` 호출보다도 먼저, "아니요" 클릭 핸들러의 맨 처음으로 옮긴다. (3) 사용자가 입력란을 직접 탭하는 경로는 `pointerdown`(포커스보다 항상 먼저 발생)에서 캡처한다. `focus` 리스너 안의 캡처는 이 두 경로 어디에도 안 걸리는 드문 경우(Tab 키 이동 등)만을 위한 안전망으로만 남긴다.
- **정착 판정 자체의 함정(두 번 반복된 시행착오)**: "스크롤이 실제로 멈췄는지" 판단하는 헬퍼(`waitForScrollSettle`류)를 만드는 과정에서 **같은 함정에 두 번 빠졌다** — (a) 1차 시도(rAF로 scrollTop을 폴링해 "N프레임 연속 무변화면 정착"): smooth 스크롤이 호출은 됐지만 실제로 움직이기 "시작"하는 시점 자체가 최대 60~70ms 지연될 수 있어(WebKit 실측), "아직 시작 안 한 정지"와 "이미 끝난 정지"를 프레임 수만으로 구분 못 했다. (b) 2차 시도(네이티브 `scroll` 이벤트 구독 + 마지막 이벤트로부터 QUIET_MS 무이벤트면 정착): 이벤트 기반으로 바꿨지만, "이벤트가 한 번도 안 오면 초기 QUIET_MS 안에 즉시 정착 처리"하는 그레이스 기간을 남겨둔 탓에 **정확히 같은 함정에 다시 빠졌다** — 그 그레이스 기간이 "스크롤이 필요 없어서 조용한 것"과 "스크롤이 필요한데 아직 시작 전이라 조용한 것"을 여전히 구분 못 했기 때문이다. **최종 해결**: 값 폴링·이벤트 유무만으로 판단하는 방식 자체를 버리고, 스크롤을 실제로 요청하는 함수(`scrollToRevealCta()`)가 "내가 스크롤을 요청했는지 여부"를 반환값으로 직접 알려주게 했다 — 요청 안 했으면 기다릴 것 자체가 없으므로 즉시 정착 처리, 요청했으면(반드시 최소 한 번은 `scroll` 이벤트가 온다는 게 보장되므로) 그레이스 기간 없이 이벤트 기반 대기만 쓴다.
- **검증**: Playwright WebKit으로 25회 반복(지터 있는 키보드 시퀀스 + 타이트한 타이밍 유지, 대기 시간을 늘려서 우회하지 않음) — A안·B안 화면 모두 `afterBlurCtaBottom`이 100% 동일값으로 수렴(간헐성 완전히 사라짐). 회귀 스윕: 바로 위 항목(갤럭시 Z 플립 튕김 히스테리시스) 재검증 0 bounces, WebKit·Chromium 양쪽에서 전체 참여자 플로우(화면1→가격A→가격B(직접입력)→SCR-004→"기타" 모달 제출) e2e 콘솔 에러 0건.
- **테스트 환경 자체의 비결정성(교훈에 포함하기엔 아까운 별도 관찰)**: 같은 RNG 시드로 같은 지터 시퀀스를 재사용해도, Playwright의 실제 실행 결과가 배치마다 달라지는 걸 여러 차례 관찰했다(예: 시드 2003이 어떤 배치에선 통과, 다른 배치에선 실패) — RNG는 "스크롤 지터 값"만 결정할 뿐 Node↔브라우저 IPC·실제 OS 스레드 스케줄링까지는 결정하지 못하기 때문이다. **디버깅 도중 "이 시드가 실패했다"는 단발성 관찰을 과신하지 않고, 항상 20회 이상 반복해 실패율로 판단해야 한다**는 실전 교훈을 얻었다.
- **교훈**: (1) **"직전에 고친 코드가 범인일 것"이라는 코디네이터의 합리적 의심도, 코드를 직접 재확인하고 대상 범위(이 경우 "열려있는 동안")만 검증해서 반증할 수 있으면 그렇게 한다** — 의심이 틀렸다고 밝혀지는 것 자체가 진짜 원인(포커스 이전 캡처 시점)을 찾는 데 필요한 전제 조건이었다. (2) **"정착(settled)을 판단하는 로직"은 값이나 이벤트의 유무만으로 만들면 거의 항상 "시작 전 정지"와 "종료 후 정지"를 혼동하는 함정에 빠진다** — 진짜 안전한 판단은 "애초에 그 동작이 실행될지 여부"를 그 동작을 시작하는 함수 자신에게 물어보는 것이다(외부에서 관찰로 추론하지 않는다). (3) **"복귀할 원래 상태"를 캡처하는 코드는, 그 캡처 이전에 실행되는 모든 부수효과(다른 UI 반응, 네이티브 브라우저 동작, CSS 트랜지션)를 전부 나열해보고 그중 가장 이른 시점보다도 먼저 캡처해야 한다** — "포커스 이벤트 안에서 캡처하면 될 것"이라는 직관은, 포커스 자체가 이미 여러 단계의 부수효과 중 하나일 뿐이라는 사실을 놓치기 쉽다.

### SCR-004 "기타" 모달에서 키보드가 열리면 "확인" 버튼이 다시 가려짐 — 재배치 자체는 정상, 카드 높이가 남은 공간보다 큰 게 원인 (상태: 해결됨 — 실기기 재확인 대기)

- **환경**: 아이폰 실기기(카카오·크롬), SCR-004 "기타" 모달("어떤 점이 좋으셨는지 자유롭게 적어주세요")의 textarea에 포커스가 들어가 키보드가 열리는 도중. 대상 함수는 참여자가 실제로 보는 경로인 `pv4CheckKeyboardOpen()`(프로토타입 뷰어) — 검토용 갤러리 카드가 쓰는 `checkKeyboardOpen()`(인스턴스 2곳, `#s4-screen`·`#s4b-screen`)은 배포 페이지(`participant-flow-deployed.html`)에서 `display:none`이라 이 재현과 무관하다.
- **혼동하기 쉬운 전제**: 바로 위 두 항목(플립4 튕김·아이폰 마진 버그)이 최근에 고쳐진 참이라, 그 수정 중 하나가 이 세 함수(`checkKeyboardOpen`×2·`pv4CheckKeyboardOpen`)에 예방적으로 얹은 히스테리시스(2026-08-27, 위 플립4 항목의 "범위 밖으로 남긴 것" 참고)가 이번에도 회귀 원인일 거라고 먼저 의심할 법했다. 하지만 실제로 코드를 다시 읽고 Playwright(가짜 `visualViewport` 하네스로 iOS 스타일 키보드 궤적을 단조 증가 시퀀스로 재현)로 직접 측정해보니, `kb-open` 토글 자체(임계값 판정, 데드존)는 정확히 설계대로 동작했다 — shrink>100px에서 정확히 한 번 켜지고 유지된다. **재배치 로직 자체는 무혐의였다.**
- **최종 원인**: `.scr004.popup.kb-open .modal-overlay { align-items:flex-start; padding-top:28px; }`는 모달 카드를 프레임(`.pv-phone`, 최대 693px)의 **위쪽**으로 붙일 뿐, 카드 자체의 높이를 "키보드가 가리지 않는 실제 남은 공간"에 맞춰 제한하지는 않는다. 이 페이지는 body가 항상 `position:fixed`(다른 두 항목에서 이미 확정한 이유로 문서 스크롤 자체를 차단)라 Safari 툴바가 스크롤 제스처로 자동 접힐 기회가 구조적으로 적고, 그 결과 `window.innerHeight`가 작은 상태(툴바가 펼쳐진 채)로 오래 유지되기 쉽다. 이런 상태에서 실제 키보드(예측 텍스트 줄 포함 ~300~360px)가 열리면 `window.visualViewport.height`가 200px 안팎까지 줄어드는데, 모달 카드 자신의 콘텐츠 높이(제목+최소 84px textarea+안내문+"확인" 버튼+패딩, 실측 약 280px)가 그보다 크다 — 카드를 위로 붙여도 카드 "자체"가 남은 가시 영역보다 커서, 카드 하단(=확인 버튼)이 여전히 키보드 아래로 밀려난다. `.screen{overflow:hidden}`이 이 초과분을 그냥 잘라버려 스크롤로도 닿을 수 없었다. Playwright로 iPhone SE급 작은 화면(innerHeight 500~560)·현실적인 키보드 shrink(최대 360px)를 조합해 재현한 결과, 수정 전 코드에서 "확인" 버튼이 가시 영역 밖으로 나가는 조합이 실제로 존재함을 확인했다(더 큰 화면·큰 innerHeight에서는 여유가 충분해 재현되지 않았다 — 화면·상태에 따라 재현 여부가 갈리는 이유).
- **해결 방법**: 재배치(align-items:flex-start)는 그대로 두고, `kb-open` 판정과 **같은 자리**에서 카드 자체의 `max-height`를 실측 `window.visualViewport.height` 기준으로(여유 56px을 뺀 값, 최소 100px 보장) 인라인으로 계산해 씌우고, `.modal-card`에 `overflow-y:auto`를 상시로 붙여 안전망을 만든다 — 카드가 남은 공간을 넘치면 카드 "안"에서 스크롤로 확인 버튼에 닿을 수 있게 한다(원인이 "카드가 뷰포트보다 크다"이므로, 처방은 "카드를 뷰포트에 맞게 제한하고 넘치는 건 내부 스크롤로 흡수한다" — 이 프로젝트에서 이미 확립된 "넘치면 스크롤로 흡수한다" 원칙을 모달 카드 레벨로 그대로 적용한 것). `kb-open`이 꺼지면(블러 시 250ms 지연 포함) `max-height`도 함께 비워 평소엔 아무 영향이 없다(콘텐츠가 이미 다 들어가므로 `overflow-y:auto`만으로는 시각적 차이가 없다).
- **검증(Playwright, 가짜 visualViewport 하네스)**: (1) 수정 전: iPhone SE급(innerHeight 500·560) + shrink 300~360px 조합에서 "확인" 버튼이 가시 영역 밖으로 나가는 걸 재현(다른 조합은 재현 안 됨 — 화면·키보드 조합에 따라 재현 여부가 갈리는 걸 실측으로 확인). (2) 수정 후: 같은 조합(최악값 innerHeight=500, shrink=360, 가시 영역 140px)에서도 카드 자체가 항상 가시 영역 안에 들어오고, 카드 내부 스크롤로 "확인" 버튼에 도달 가능함을 확인. (3) `layoutShrunk=true`(Android 스타일, 레이아웃 뷰포트 실측 축소)를 강제 재현해 이 분기에서는 `max-height`가 빈 값으로 유지됨을 확인(프레임이 이미 CSS(`dvh`)로 줄어드는 기존 설계와 충돌 없음). (4) 회귀 스윕 — 희망가 입력 화면(`priceInputKbCheck`, 완전히 다른 함수·다른 상태 변수)은 이번 수정에서 단 한 줄도 건드리지 않았음을 grep으로 먼저 확인한 뒤, 100px 경계 순수 지터 시퀀스(WebKit·Chromium)로 `scrollTop` 방향 반전 0회 재확인. (5) 전체 참여자 e2e 플로우(화면1→가격A(직접입력)→SCR-004 A/B+이유 선택→"기타" 모달 6자 이상 입력→확인→제출→SCR-005 도달)를 WebKit·Chromium 양쪽에서 콘솔/페이지 에러 0건, `goTo(6)`까지 정상 도달 확인. (6) 로컬 정적 문법 검사(`new Function()`)로 9개 `<script>` 블록 전부 손상 없음 재확인.
- **교훈**: (1) **"재배치가 됐는가"와 "재배치된 요소 자체가 남은 공간에 들어가는가"는 서로 다른 질문이다** — `kb-open` 토글·`align-items` 변경 같은 "어디로 옮길지"를 고치는 수정은, "옮긴 자리에 그 요소가 다 들어가는지"(크기 문제)까지는 저절로 해결해주지 않는다. 이 프로젝트에서 이미 위 두 항목이 다룬 "CTA가 넘쳐서 클리핑된다" 패턴과 근본적으로 같은 종류의 버그가, 재배치 로직이 이미 존재하는 곳에서도 별도로 재발할 수 있다는 사례다. (2) **직전에 고친 코드(히스테리시스)를 1차 용의선으로 의심하는 건 합리적이지만, 코드를 직접 다시 읽고 재현 테스트로 반증할 수 있으면 그렇게 해서 진짜 원인을 좁힌다** — 이번에도 의심이 틀렸다고 확인하는 과정 자체가 진짜 원인(카드 높이 vs 가시 영역)을 찾는 전제 조건이었다. (3) **"body가 position:fixed라 문서 스크롤이 없다"는 이 페이지 특유의 설계가, Safari 툴바 자동 접힘 기회를 줄여 `window.innerHeight`가 작은 상태로 오래 유지되는 부작용을 낳을 수 있다** — 다른 키보드 관련 버그를 진단할 때도 이 페이지에서는 "툴바가 안 접힌 상태"를 기본 가정으로 두는 게 안전하다.

## 근거

2026-08-27, 같은 화면 찌그러짐/여백 버그를 이미 두 차례(카카오 전용 → 아이폰/안드로이드 Chrome까지 확장) 수정 완료로 보고했는데도 계속 재발하다가, 데스크톱 웹에서도 재현된다는 사용자 제보로 진단 방향 자체가 잘못됐음이 드러났다. 이 시행착오를 계기로, AB테스트 프로젝트에 국한되지 않고 이후 다른 앱·웹 프로젝트에서도 참고할 수 있는 이식 가능한 버그 진단 로그를 만들어달라는 요청을 받아 이 문서를 신설했다. 이후 Playwright 기반 DOM 실측으로 최종 원인(정적 레이아웃 오버플로)이 확정돼 상태를 "해결됨"으로 갱신했다. 같은 날, "화면 튕김" 수정이 실기기에서 재발했다는 재보고를 계기로 세 번째 항목(희망가 입력란 키보드 감지 로직)을 추가했다 — 앞선 두 항목과 달리 이번엔 "이전 수정의 회귀"가 아니라 "이전 수정이 커버하지 않는 다른 코드 경로"였다는 점에서 진단 패턴이 다르다. 같은 날 또다시, 세 번째 항목의 수정 직후 "키패드 마진 버그"가 실기기에서 재발했다는 보고를 계기로 네 번째 항목을 추가했다 — 코디네이터가 세 번째 항목의 수정을 1차 용의선으로 지목했으나 실제로는 완전히 별개의 "포커스 전 scrollTop 캡처 시점" 문제였고, 그 해결 과정에서 "정착 판단 로직"의 같은 함정에 두 번 빠졌다가 세 번째 접근(호출부가 직접 알려주는 방식)으로 확정했다. 같은 날 다섯 번째로, SCR-004 "기타" 모달의 키보드 대응(예방적 히스테리시스가 이미 적용된 함수)이 실기기에서 "확인" 버튼이 다시 가려지는 형태로 재발했다는 보고를 계기로 다섯 번째 항목을 추가했다 — 직전 수정(히스테리시스)에 대한 의심은 재확인 결과 무혐의였고, 실제 원인은 "재배치는 되지만 재배치된 카드 자체가 남은 가시 영역보다 크다"는, 이전 네 항목과는 또 다른 새로운 패턴이었다.
