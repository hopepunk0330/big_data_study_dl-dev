# planning-doc-qa 계약 (재사용 가능한 패턴)

`docs/planning/*.md`(PM 기획 문서 + ML 계획 문서 전체 — 정확한 번호 범위는 프로젝트마다 다르므로 그 프로젝트의 진행보드를 참고한다, `ml-project-workflow.md` 11절과 같은 원칙)를 새로 만들거나 버전업한 직후 자동으로 검토·보완하는 `planning-doc-qa` 에이전트의 판단 기준·수정 범위·절차를 정의한다. `data-harness-auditor`(하네스 대상, 읽기 전용)와는 대상·권한이 다르므로 혼동하지 않는다 — 이 계약은 그 차이를 전제로 쓴다.

## 1. 실행 시점

`docs/planning/`에 새 문서를 만들거나 기존 문서를 버전업하는 작업 라운드가 끝나면, 사용자가 물어보지 않아도 곧바로 실행한다(`CLAUDE.md` 행동 지침 참고) — `data-harness-auditor`가 하네스 수정 후 자동 실행되는 것과 같은 패턴을 문서 도메인에 적용한 것이다.

- 한 라운드 안에서 여러 문서를 연달아 고치는 중이라면, 문서마다 돌리지 않고 그 요청이 다 끝난 뒤 한 번 실행한다.
- `ml-doc-writer`가 초안을 작성한 직후에도 실행한다 — `ml-doc-writer`는 Notion을 건드리지 않으므로(그 계약 문서 참고), 로컬 초안의 최종 검토·Notion 반영은 이 에이전트가 이어받는다.

## 2. 점검 기준 4가지

### 2-1. 구조 완전성

`notion-workflow.md` 4-4·4-5절이 정한 표준 구조가 빠짐없이 있는지 확인한다:
- 메타 표(문서유형/버전/상태)
- "이 문서가 다루는 것 / 안 다루는 것" 콜아웃 — 있는지뿐 아니라 **완전한지**도 확인한다: 이 문서가 언급하는 개념(툴 이름, 구현 방식 등) 중 상세 설명 없이 지나간 게 있으면, "안 다루는 것" 목록에 그게 정확히 어느 문서·어느 절 몫인지 짚혀 있는지 대조한다. "다른 문서에 있다"는 식으로 뭉뚱그렸거나 아예 빠져 있으면 구조 완전성 위반으로 취급한다.
- ID 체계(해당하는 문서 유형이면 FR/AC/SCR/FN 등)와 ID 매핑 표
- "근거" 절 — 인용하는 다른 문서·외부 자료 목록

### 2-2. 내용 전문성 — 구조가 맞아도 내용이 빈약하면 통과시키지 않는다

이게 이 에이전트의 핵심 차별점이다. 문서 유형에 따라 다른 전문 기준을 적용한다:

- **PM 문서(원페이저~리스크체크리스트)**: 핵심 주장에 근거가 붙어 있는가(사후 추측이 아니라 실제 데이터·자료 인용), 실험 설계라면 혼입 변수를 놓치지 않았는가, 완료 기준(AC)이 제3자가 판정 가능한 문장인가, 리스크가 추상적 나열이 아니라 구체적 완화 방안을 갖는가.
- **ML 문서(데이터명세서~재현성가이드)**: 수치가 실제로 재현 가능한 근거를 달고 있는가(추측성 서술 금지), 통계적 주장(상관·검정)이 방법 선택 근거까지 설명하는가, 데이터 누수 위험 지점을 놓치지 않았는가.
- 판단이 애매하면 실제로 코드를 돌려 검증한다(Bash 사용 가능) — "아마 맞을 것"으로 넘어가지 않는다.

### 2-3. 문서 간 캐스케이드 정합성 — 하네스 감사와 같은 원칙을 문서 도메인에 적용

**한 문서의 결정이 바뀌면 그 결정을 인용하는 다른 문서들이 전부 최신 상태인지 양방향으로 확인한다.**

- **역방향(이 문서 → 인용 대상)**: 이 문서가 "PRD v1.6에 따르면..."처럼 다른 문서를 인용할 때, 그 버전이 실제 최신 버전과 일치하는지 해당 파일을 직접 열어 확인한다.
- **정방향(이 문서 ← 이 문서를 인용하는 다른 문서들)**: 이번에 버전업된 이 문서의 핵심 결정을 인용하고 있는 다른 `docs/planning/*.md` 파일이 있는지 `grep`으로 찾아, 그 파일들도 이 새 결정을 반영했는지 확인한다. 예: 06번 화면정의서가 상품 예시를 바꾸면, 03_PRD의 FR-01·FR-06, 05_실험설계서의 실험 변형 절, 07_리스크체크리스트의 관련 리스크 행도 같이 갱신됐는지 확인한다.
- Notion 메인 페이지(그 프로젝트의 관리용 페이지 — ID는 프로젝트마다 다르므로 하드코딩하지 않고, 모르면 이전 세션 기록(대화 맥락)에서 찾거나 사용자에게 URL을 요청한다)의 관련 섹션(예: 이 프로젝트라면 "✅ A/B 내용 확정" 콜아웃, "분석 목표 체계" 표)도 캐스케이드 대상에 포함한다 — `notion-workflow.md` 4-1절의 "정합성 체크" 규칙과 동일 원칙.

### 2-4. 서식 — Notion 반영 전 로컬 파일 단계에서 미리 걸러낸다

`notion-workflow.md` 4-3절의 금지 규칙(raw HTML 태그, HTML 엔티티, 인라인 코드를 걸치는 굵게)을 로컬 `.md` 파일에서 먼저 점검한다 — Notion에 올린 뒤 걸러내는 것보다 먼저 잡는 게 싸다. Notion 반영 시에는 4-2절의 회색 비강조 규칙(Claude가 조사·작성한 설명은 `<span color="gray">`로 감싸고, 같은 목록 중간이 아니라 맨 끝에 배치)도 함께 적용한다 — 이 규칙은 Notion 전용이라 로컬 `.md` 단계에서는 적용하지 않는다.

## 3. 문제를 발견하면 — 직접 고친다

`data-harness-auditor`와 달리 이 에이전트는 **쓰기 권한이 있다.** 문제를 발견하면:

1. 내용이 실질적으로 바뀌는 수정이면 `notion-workflow.md` 4-1절 5번의 버전업 규칙을 그대로 따른다 — 기존 파일을 그 자리에서 고치고 끝내지 않고, **새 버전 파일을 새로 쓴 뒤, 진짜 구버전 스냅샷을 `docs/planning/old/`로 보존**한다(버전 뒤섞임 버그 방지 — 상세 절차는 이 세션의 실제 관행을 그대로 따른다: 기존 파일이 커밋돼 있으면 `git show <커밋>:<경로>`로 진짜 구버전을 추출, 아니면 현재 파일을 그대로 old/에 복사).
2. 오타·서식 버그처럼 내용 변경이 아닌 수정은 버전을 새로 올리지 않고 같은 파일에 바로 고친다.
3. 수정 후 반드시 **로컬 파일을 다시 읽어 결과를 확인**한다.

## 4. Notion 반영

수정이 끝나면 Notion까지 동기화한다 — `notion-workflow.md` 4-1절 워크플로우(제목의 버전 표기 갱신 → 본문을 `notion-update-page` 도구로 반영(부분 교체는 `command: "update_content"`, 전체 교체는 `command: "replace_content"` — 같은 도구의 서로 다른 모드) → `notion-fetch`로 재조회해 렌더링 확인)를 그대로 따른다. 해당 문서의 Notion 하위 페이지 ID를 모르면, 그 프로젝트의 Notion 메인 페이지를 먼저 조회해 "기획 문서"/"ML 파이프라인 계획" 같은 섹션의 페이지 링크에서 찾는다.

**새 문서를 처음 하위 페이지로 만들 때, 표준 문서 카탈로그(이 프로젝트에서는 00~11·17번 목록 — 실제 번호는 프로젝트마다 다르다) 자리에는 mention-page로 때우지 않는다** — `notion-create-pages`가 만든 `<page>` 블록이 자동으로 페이지 맨 끝에 붙는 문제(`notion-workflow.md` 4-1절)를 mention-page로 우회하면, 그 문서만 형제 문서들과 달리 색상 카드가 아니라 단순 링크로 보여 눈에 띄게 어긋난다. 이 카탈로그 자리는 항상 사용자에게 Notion 앱에서 직접 드래그해달라고 요청하고, mention은 사용자가 "링크만 있어도 된다"고 명시적으로 확인해준 경우에만 쓴다(`notion-workflow.md` 4-1절 참고, 2026-08-27 실사고로 신설).

## 5. 하지 않는 것 (메인 세션 몫)

- **로컬 git commit** — 이 에이전트는 파일을 쓰고 Notion에 반영하는 데까지만 하고, 커밋은 메인 세션이 결과를 확인한 뒤 한다(`git-workflow.md` 3-1절의 "로컬 커밋은 매번 허락받지 않는다"는 메인 세션의 습관이지, 이 에이전트에게 위임된 권한이 아니다).
- **Notion 진행보드의 "완료" 상태 변경** — `notion-workflow.md` 5절 규칙대로, "완료"는 사용자가 검토 후 명시적으로 신호를 줘야만 바뀐다. 이 에이전트가 검토를 마쳤다고 자동으로 완료 처리하지 않는다.
- **`git push`** — 애초에 이 에이전트 권한 밖이며, 메인 세션도 매번 명시적 허락을 받아야 하는 영역이다.
- **문서의 핵심 방향 자체를 재설계** — 이 에이전트는 이미 확정된 결정이 문서 전반에 일관되게 반영됐는지 검증·보완하는 역할이지, "이 실험 설계 자체가 맞나"를 처음부터 다시 정하는 역할이 아니다. 근본적인 설계 결함을 발견하면 직접 재설계하지 않고 보고해서 사용자·메인 세션의 판단을 받는다.

## 6. 근거

이 계약은 이 프로젝트의 실제 세션에서 09~11번 ML 문서에 근거 절 누락·서식 버그·오래된 상호참조가 반복적으로 발견돼 매번 메인 세션이 수작업으로 잡아낸 것을 계기로 만들어졌다(`docs/harness/HARNESS_LOG.md` 참고). `data-harness-auditor`(`docs/harness/`와 무관한 별도 감사 대상)와 `ml-doc-writer-contract.md`(ML 문서 작성 전용, Notion 미반영)의 역할 경계를 참고해 설계했다.
